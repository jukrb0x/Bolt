Plugins import `boltstack` and `zod`. The running `bolt` process injects one instance of each. `definePlugin` and `PluginBase` stamp `Symbol.for("boltstack.plugin")` and the plugin's declared `apiVersion`. It defaults to `1`. This bolt accepts plugin API `1` and `2` (`SUPPORTED_PLUGIN_API_VERSIONS`; `PLUGIN_API_VERSION` is `2`, the highest). Plugin API v2 adds [handler results](#handler-results-plugin-api-v2), [capability tags](#capability-tags-plugin-api-v2), `ctx.emit`, and [config hooks](#config-hooks-plugin-api-v2). See [Migrating to plugin API v2](/guides/migrating-to-plugin-api-2).

## Frozen

Plugin API v2 is frozen. Until a plugin API v3, which requires a bolt major version, this surface is append-only. That covers `bolt.d.ts` (handler results, capability tags, `ctx.emit`, and the config hooks `validateConfig`, `aiContext`, `aiPathRoots`, and `initDetect`), this page, and the migrating guide. Existing fields, hook signatures, and `HandlerResult.status` values keep their meaning. New optional fields may be added.

Removing or reinterpreting an existing field, making `emit` required with no transition, changing `HandlerResult.status`, or changing a hook signature incompatibly requires plugin API v3.

`bolt version --json` lists `2` in `plugin_api` and `plugin-api-2` in `capabilities`. It does not list a `config-hooks` capability. Config hooks are part of plugin API v2, not a separate capability.

The runtime manifest is not authored as YAML. `defineHandler` and `@handler` fill it in memory when the plugin is defined. Separately, `bolt ai` reads the serializable catalog file `bolt.plugin.json` (see [Plugin System](/guides/plugin-system)); refresh it with `bolt plugin build`.

## definePlugin

```typescript
import { defineHandler, definePlugin } from "boltstack";
import type { BoltPluginContext } from "boltstack";
import { z } from "zod";

export default definePlugin({
  namespace: "deploy",
  version: "0.1.0",
  description: "Ship a build",
  handlers: {
    to_s3: defineHandler(
      {
        description: "Upload to ${bucket}",
        ai: true,
        params: z.object({
          bucket: z.string().describe("Destination bucket"),
          region: z.string().default("us-east-1"),
        }),
      },
      async (params, ctx: BoltPluginContext) => {
        ctx.logger.info(`Deploying to ${params.bucket} (${params.region})`);
        if (ctx.dryRun) return;
        ctx.logger.info(`Project: ${ctx.cfg.project.name}`);
      },
    ),
  },
});
```

| Field         | Required | Notes                                                                                                                                                          |
| ------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `namespace`   | yes      | Used as `uses: namespace/handler`                                                                                                                              |
| `version`     | yes      | Plugin version string, not the CLI version                                                                                                                     |
| `description` | yes      | Plugin summary                                                                                                                                                 |
| `apiVersion`  | no       | `1` or `2`. Omitted means `1`. Declare `2` for capability tags and results                                                                                     |
| `metadata`    | no       | Zod schema for this plugin's opaque `config`. Core JSON Schema does not describe those fields. `loadConfig` checks `metadata` when the plugin entry is present |
| `handlers`    | yes      | At least one `defineHandler()` result                                                                                                                          |

`definePlugin` used to return a descriptor for `withDescriptor`. It now returns the plugin object.

A plugin that exposes a `manifest` getter without `Symbol.for("boltstack.plugin")` is rejected. A branded plugin whose `apiVersion` is not `1` or `2` is rejected; a higher version tells you to run `bolt self-update`. A branded export with no `apiVersion` at all is rejected too. The registry does not rewrite a foreign `apiVersion`.

## defineHandler

```typescript
defineHandler(meta, fn);
```

| Field         | Default | Notes                                                                                                                             |
| ------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `description` | none    | Task line. `${name}` is replaced from params                                                                                      |
| `ai`          | `false` | `false`, `true`, or `"confirm"`. A human `bolt run` does not prompt. Agent execute of `"confirm"` requires `--confirmed-by-user`. |
| `params`      | none    | Flat zod object. Checked before `fn` runs                                                                                         |
| `capability`  | none    | Tag or tags, e.g. `"doctor"`. Requires `apiVersion: 2`                                                                            |

Allowed param fields: `z.string()`, `z.enum()`, `z.coerce.number()`, `z.coerce.boolean()`, with `.optional()`, `.default()`, and `.describe()` only.

`fn` receives the parsed params and a `BoltPluginContext`. It may return a `HandlerResult`. Bolt acts on it only when the plugin declares `apiVersion: 2`. A plugin API v1 return value is ignored.

## Handler results (plugin API v2)

```typescript
import { defineHandler, definePlugin, fail, ok, warn } from "boltstack";

export default definePlugin({
  namespace: "ue",
  version: "1.3.0",
  description: "Unreal helpers",
  apiVersion: 2,
  handlers: {
    doctor_ddc: defineHandler({ ai: true, capability: "doctor" }, async () => {
      const missing = await sharedDdcMissing();
      if (!missing) return ok();
      return warn("Shared DDC path unreachable", {
        diagnostics: [
          {
            level: "warn",
            code: "DDC_SHARED_MISSING",
            message: "Shared DDC path unreachable",
            fix: "Set [DerivedDataBackendGraph] Shared Path",
          },
        ],
      });
    }),
  },
});
```

```typescript
interface HandlerResult<D extends JsonValue = JsonValue> {
  status: "ok" | "warn" | "fail" | "skipped";
  summary?: string; // one line, at most 200 characters
  data?: D; // JSON only
  artifacts?: { kind: string; path: string; sha256?: string; size?: number; label?: string }[];
  diagnostics?: {
    level: "info" | "warn" | "error";
    code?: string; // UPPER_SNAKE_CASE
    message: string;
    file?: string;
    line?: number;
    fix?: string;
  }[];
  next?: { ref: string; params?: Record<string, string>; reason?: string }[]; // shown, never run
  schema?: string; // reserved, not checked
}
```

| Return value (v2 plugin)                                                         | Effect                                                                    |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `undefined`                                                                      | `ok`                                                                      |
| `ok` / `warn` / `skipped`                                                        | Step succeeds. The summary and diagnostics are printed                    |
| `fail`                                                                           | Step fails like a throw (`continue_on_fail`, notifications, exit code)    |
| bad `status`, wrongly typed known field, non-JSON `data`, not a plain object     | Step fails with `RESULT_INVALID`, naming the field and the fix            |
| unknown field (top level or inside a diagnostic, artifact, or next step)         | Warning `RESULT_UNKNOWN_KEY`. The field is dropped. The step is unchanged |
| over a limit (8 KiB strings, 200 diagnostics/artifacts, 20 next, 256 KiB result) | Warning `RESULT_TRUNCATED`. The value is cut. The step is unchanged       |

On `fail`, `onAfterStep` runs first, then the step fails with `HANDLER_FAILED`. The message is the summary, or the first error diagnostic, or `<ref> returned status "fail" without summary`. Backslashes in `diagnostics[].file` and `artifacts[].path` become `/`.

`ok`, `warn`, `fail`, and `skipped` exist only on a bolt that supports plugin API v2. A v1 plugin that must run on older bolts returns an object literal instead.

## Events

```typescript
ctx.emit?.({ type: "progress", message: "cooking", progress: { current: 1, total: 3 } });
ctx.emit?.({ type: "log", message: "cache warm" });
```

`ctx.emit` works for v1 and v2 plugins and for `onInit`, `onBeforeStep`, and `onAfterStep`. It is synchronous and never throws. Bolt stamps each event with a run-wide `seq`, the step `ref`, and the step path. `type` uses lowercase dot-separated words. Invalid events are dropped with one `EVENT_INVALID` warning per type. An event sent after the step settled (the handler and `onAfterStep` finished) is dropped with one `EMIT_AFTER_SETTLE` warning (usually a missing `await`). At most 10,000 events per step are kept.

Events are printed on the run output and written to the existing text run log (`.bolt/logs/bolt_<timestamp>.log`). `log` events print as info lines; other types print as a step detail line, for example `ue/build progress 1/3: cooking`. There is no structured JSONL run log yet (that is **BOLT-AI-2**); there is no `--json=ndjson`. Library callers can pass `onEvent` to `Runner`.

`emit` is optional in `BoltPluginContext`, because bolts older than plugin API v2 do not provide it. Call `ctx.emit?.(...)`. `BoltPluginContextV2` is the same type with `emit` required, for v2 plugins that prefer it.

## Capability tags (plugin API v2)

A handler can declare the roles it fills with `capability`. Core uses tags to find handlers by role instead of by name.

| Form          | Example        | Notes                                                                                                           |
| ------------- | -------------- | --------------------------------------------------------------------------------------------------------------- |
| Core tag      | `doctor`       | `doctor`, `diagnose`, `detect`, `notify`, `vcs.sync`, `vcs.info`, `vcs.revision`, `artifact.store`, `env.check` |
| Vendor tag    | `x-acme.audit` | `x-<vendor>.<name>`                                                                                             |
| Own namespace | `ue.cook`      | `<namespace>.<name>` of the declaring plugin                                                                    |

Unknown bare tags are rejected with a "did you mean" hint. The areas `doctor`, `diagnose`, `detect`, `notify`, `vcs`, `artifact`, and `env` are reserved for core tags, even for a plugin whose namespace matches. A handler has at most 8 tags. Tags are static: they must not depend on config.

`env.check` is the tag for `bolt env probe` and `bolt env ensure`. The handler also sets `checkId` to a stable id. Core calls `findByCapability("env.check")` and runs the handler whose `checkId` matches the declared id. It does not run every tagged handler. `ctx.envCheck` is an optional field on the context (`id`, `require`, and `version` and `params` when the manifest sets them). `action` is `"ensure"` only when ensure is applying that gap. Probe leaves `action` unset. Older bolts omit the whole field, so plugins read `ctx.envCheck?.id` and treat a missing `action` as probe. The handler function signature is unchanged.

Optional `studioSetupShell: true` marks that handler as a one-shot setup script. The manifest field is `studio_setup_shell`. `bolt env ensure` exits 2 with `EMPTY_SHELL` and does not call the handler. Probe still can. A handler that calls an installer and returns boolean `data.changed` does not set this flag. The option is additive on plugin API v2.

A plugin that uses `capability` without `apiVersion: 2` fails when it is defined (function plugins) or registered (class plugins), with the fix in the message.

Singleton tags are chosen with the top-level `capabilities:` map (`bolt.local.yaml` wins per key). Fan-out tags ignore that map. See [Choosing a singleton provider](/guides/migrating-to-plugin-api-2#10-choosing-a-singleton-provider).

## Class plugins

```typescript
import { PluginBase, handler } from "boltstack";
import type { BoltPluginContext } from "boltstack";
import { z } from "zod";

export default class DeployPlugin extends PluginBase.withDescriptor({
  namespace: "deploy",
  version: "0.1.0",
  description: "Ship a build",
}) {
  @handler({
    description: "Upload to ${bucket}",
    params: z.object({ bucket: z.string() }),
  })
  async to_s3(params: { bucket: string }, ctx: BoltPluginContext) {
    ctx.logger.info(params.bucket);
  }
}
```

`@handler("...")` still works. The object form takes `description`, `ai`, `params`, `alias`, and `capability`. A class plugin declares plugin API v2 with the instance field `apiVersion = 2;`. A `static apiVersion` is not read by bolt: it is an error when it differs from the instance field and a warning when it matches. Only decorated methods become handlers. `onInit`, `onBeforeStep`, and `onAfterStep` are lifecycle hooks on the instance. They are not copied into the manifest.

The host compiles class files with legacy decorators. It does not read the project's `tsconfig`.

## Config hooks (plugin API v2)

Config hooks are part of the plugin API v2 public surface. Set `apiVersion` to `2` before implementing one. Bolt calls a hook when the method exists, including on a plugin that left `apiVersion` at `1`. `bolt check` warns in that case: `Set apiVersion = 2 on plugin <namespace>`.

```typescript
interface ConfigIssue {
  path: string;
  message: string;
  code?: string;
  hint?: string;
}

validateConfig?(input: {
  namespace: string;
  config: unknown | undefined; // omitted when the plugins entry has no config
  present: boolean; // false when plugins[] has no entry for this namespace
  tasks: Record<string, unknown>;
  configPath: string;
}): ConfigIssue[];

aiContext?(input: { cfg: BoltPluginConfig; configDir: string }): {
  markdown?: string[];
  info?: Record<string, unknown>;
};

aiPathRoots?(input: { cfg: BoltPluginConfig; configDir: string }): Array<{
  refs: string[];
  params: string[];
  root: string;
  label: string;
}>;

/** Reserved. bolt init does not call this. */
initDetect?(dir: string): { kind: string; summary: string } | null;
```

`validateConfig` runs from `loadConfig` and `bolt check` after the core schema succeeds. Bolt calls it on every built-in, whether or not `bolt.yaml` has an entry for it, and on every external plugin this config loaded. `present` is false and `config` is undefined when `plugins[]` has no entry. A plugin that exposes `metadata` (a Zod schema) is checked only when `present` is true. A schema failure is `CONFIG_PLUGIN_INVALID` (exit 3) at `plugins.<namespace>.config…`. Domain rules, such as tasks that reference the plugin, belong in `validateConfig`, not in that schema.

A task `uses:` value of `namespace/handler` whose namespace is not a built-in and not a `plugins[]` entry is `CONFIG_PLUGIN_REQUIRED` (exit 3). The hint is `Add a plugins entry for "<namespace>" or install the plugin.` A built-in that is registered but missing from `bolt.yaml` writes its own hint. A return value that is not `ConfigIssue[]`, or a hook that throws, is `CONFIG_PLUGIN_HOOK`.

`bolt ai` appends `aiContext().markdown` after the plugin catalog. `bolt info --json` shallow-merges `aiContext().info` into `data`. Built-ins run first, then `plugins[]` path plugins. A missing or empty `info` is skipped; the same key later overwrites. `aiPathRoots` and `initDetect` are typed on the plugin. `bolt init` does not call `initDetect`. `aiPathRoots` does not replace the path checks bolt already applies to handlers such as `git/info`.

## Brand

```typescript
Symbol.for("boltstack.plugin");
```

`definePlugin` and the `PluginBase` constructor set that symbol and the declared `apiVersion` (default `1`). `instanceof` is not the check. Two copies of the library would fail `instanceof` even when the protocol matches, so the registry reads the shared symbol and the numeric `apiVersion`.

Plain handler maps with no brand still load. Their manifest is reflected as `ai: false` and no params. New plugins should use `definePlugin`.

## BoltPluginContext

```typescript
interface BoltPluginContext {
  cfg: BoltPluginConfig;
  configDir: string;
  dryRun: boolean;
  logger: BoltLogger;
  runtime: Runtime;
  emit?: (event: BoltEvent) => void; // see Events
}
```

`cfg.project` is `{ name }`. Engine paths and targets are not fields of `project`. They are `cfg.plugins` entries. The `ue` entry's `config` holds `engine`, `project`, `uproject`, and `targets`.

`configDir` is the directory that contains `bolt.yaml`. Relative plugin paths resolve against it.

`runtime` is `spawn`, `spawnSync`, `shell`, and `parseYaml`.

`dryRun` is true when `--simulate` was passed (or `dryRun: true` in the library API, which still behaves like `--simulate`; a pure library dry run is tracked as BOLT-DX-3). Return before side effects. `--dry-run` never loads plugins, so handlers and hooks are not called.

For unit tests, `createTestContext(overrides?)` returns a context with a silent logger, a runtime stub, and `emit` recording into `.events`.

```typescript
interface BoltLogger {
  info(msg: string): void;
  warn(msg: string): void;
  error(msg: string): void;
  debug(msg: string): void;
  cmd(msg: string): void;
}
```

## bolt.yaml

Core keys are generic. `version` is `1`. There is no root `targets` field. `plugins[].config` is opaque in the core schema. The plugin's `metadata` schema and `validateConfig` validate it.

```yaml
version: 1

project:
  name: MyGame

plugins:
  - namespace: ue
    config:
      engine:
        path: C:/UnrealEngine
        vcs: git
      project:
        path: C:/Projects/MyGame
        vcs: svn
      uproject: C:/Projects/MyGame/MyGame.uproject
      targets:
        editor:
          kind: editor
          config: development

tasks:
  deploy:
    - uses: deploy/to_s3
      with:
        bucket: my-game-builds
        region: us-east-1
```

## Types

Import from `"boltstack"`. The release asset `bolt.d.ts` is wrapped as `declare module "boltstack"`. `bolt plugin new` puts `boltstack` in `devDependencies` for that module name. The host still injects the runtime module. Do not bundle a second `boltstack` or a second `zod`.
