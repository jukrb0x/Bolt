---
title: "Migrating to plugin API v2"
description: "When to declare apiVersion 2, how results, events, capability tags, and config hooks behave, and what older bolts do with your plugin."
---

Plugin API v2 adds handler results that bolt acts on, `ctx.emit` events, capability tags, and config hooks. Existing plugins keep working unchanged. A plugin without `apiVersion` is plugin API v1.

## 1. Do you need v2?

| You want                                                                  | Plugin API                     |
| ------------------------------------------------------------------------- | ------------------------------ |
| Progress or log events                                                    | v1 is enough. Use `ctx.emit?.` |
| Return values only for your own tests                                     | v1 is enough                   |
| `capability` tags                                                         | v2                             |
| A returned `fail`, `warn`, `data`, or diagnostics bolt acts on            | v2                             |
| Config hooks (`validateConfig`, `aiContext`, `aiPathRoots`, `initDetect`) | v2                             |

Config hooks need `apiVersion: 2`. Bolt calls a hook when the method exists. `bolt check` warns `Set apiVersion = 2 on plugin <namespace>` when a hook is present and `apiVersion` is not 2. `validateConfig` runs during config load. `aiContext` runs for `bolt ai` and `bolt info --json`. `aiPathRoots` and `initDetect` are on the type surface; `bolt init` does not call `initDetect`. See [Config hooks](/api/plugin-api#config-hooks-plugin-api-v2).

## 2. Minimum bolt

Check the bolt you need to support:

```bash
bolt version --json
```

Declare `apiVersion: 2` only when `plugin_api` includes `2` and `capabilities` includes `plugin-api-2`. The first release with plugin API v2 is `bolt <X>`. An older bolt prints only a version string for `bolt version --json`; treat it as plugin API v1 only.

## 3. Declaring v2

Function plugins:

```typescript
export default definePlugin({
  namespace: "ue",
  version: "1.3.0",
  description: "Unreal helpers",
  apiVersion: 2,
  handlers: {/* ... */},
});
```

Class plugins use the instance field, not `static`:

```typescript
export default class UePlugin extends PluginBase.withDescriptor({
  namespace: "ue",
  version: "1.3.0",
  description: "Unreal helpers",
}) {
  apiVersion = 2;
}
```

Bolt does not read `static apiVersion`. An older bolt would load such a plugin as v1 and silently drop its tags. A new bolt rejects a `static apiVersion` that differs from the instance field and warns when they match.

## 4. Behaviour on older bolts

| Plugin                           | Bolt without plugin API v2                                                                            |
| -------------------------------- | ----------------------------------------------------------------------------------------------------- |
| v2 function plugin               | Fails when loaded: `definePlugin: apiVersion 2 is not supported. This bolt implements plugin API v1.` |
| v2 class plugin                  | Fails when registered: `Plugin "ue" requires plugin API v2, but this bolt supports plugin API v1.`    |
| v1 plugin calling `ctx.emit?.()` | Silent no-op                                                                                          |
| v1 plugin calling `ctx.emit()`   | `TypeError`: `ctx.emit` is undefined, and the step fails                                              |
| v1 plugin importing `ok`/`fail`  | The import is undefined, so calling it throws                                                         |
| Any returned result              | Ignored                                                                                               |

Those two error messages come from bolts that predate v2 and cannot be changed. The fix is to upgrade bolt (`bolt self-update`).

On a bolt with plugin API v2, a plugin that asks for a newer plugin API than it supports gets an error that says to run `bolt self-update`.

## 5. Emitting events portably

```typescript
ctx.emit?.({ type: "progress", message: "reading .uproject", progress: { current: 1, total: 2 } });
```

`?.` keeps the call safe on older bolts. Events are shown on the run output and in `.bolt/logs/bolt_<timestamp>.log`. See [Events](/api/plugin-api#events).

`BoltPluginContext.emit` stays optional until the next plugin API major version. v2 plugins that want it required can type the context as `BoltPluginContextV2`.

## 6. Returning results

With `apiVersion: 2`, return `ok()`, `warn()`, `fail()`, `skipped()`, or a matching object literal. Returning nothing counts as `ok`.

- `fail` fails the step exactly like a throw. `onAfterStep` still runs first.
- A bad `status`, a wrongly typed known field, or non-JSON `data` fails the step with `RESULT_INVALID`. The message names the field.
- An unknown field only warns (`RESULT_UNKNOWN_KEY`) and is dropped. A plugin that uses a field added by a newer bolt still runs on an older one.

v1 plugins can return object literals for their own tests. Bolt ignores them. Do not import the constructors in a v1 plugin that must run on older bolts.

## 7. Tagging handlers

```typescript
info: defineHandler({ ai: true, capability: "detect" }, async () => ok()),
doctor_ddc: defineHandler({ ai: true, capability: ["doctor", "ue.ddc"] }, async () => ok()),
```

```typescript
@handler({ capability: ["vcs.sync"] })
async sync() {}
```

Allowed: core tags (`doctor`, `diagnose`, `detect`, `notify`, `vcs.sync`, `vcs.info`, `vcs.revision`, `artifact.store`, `env.check`), `x-<vendor>.<name>`, and `<your-namespace>.<name>`. The areas `doctor`, `diagnose`, `detect`, `notify`, `vcs`, `artifact`, and `env` are reserved for core tags. At most 8 tags per handler. Tags must not depend on config. Plain object plugins (a hand-written `handlers` map) cannot carry tags. Convert them to `definePlugin`.

`env.check` also takes `checkId`. `bolt env probe` and `bolt env ensure` pass the declaration on optional `ctx.envCheck`. Read `ctx.envCheck?.id`. `action` is `"ensure"` only while ensure is filling that gap. A missing `action` means probe, including on older bolts that omit `ctx.envCheck`. Optional `studioSetupShell: true` is an additive flag for a one-shot setup script. It does not change the handler signature. `bolt env ensure` exits 2 with `EMPTY_SHELL` and does not call that handler.

## 8. Tests

```typescript
import { createTestContext } from "boltstack";

const ctx = createTestContext({ dryRun: true });
const result = await plugin.handlers.info({}, ctx);
expect(ctx.events).toEqual([{ type: "progress", progress: { current: 1, total: 2 } }]);
```

Hand-written context mocks keep compiling because `emit` is optional.

## 9. After upgrading bolt

Regenerate the AI context with `bolt ai`. The plugin manifest format changed (`bolt version --json` reports `manifest_format: 2`), capability tags now appear in the catalog, and the built-in `git` and `svn` handlers changed their `ai` permissions.

Core looks handlers up with `PluginRegistry.findByCapability()`. Choosing among several providers for a singleton tag is the top-level `capabilities:` map (BOLT-EXT-2), not part of plugin API v2 itself.

## 10. Choosing a singleton provider

`doctor`, `diagnose`, `detect`, and `notify` are fan-out: every matching handler runs, and a `capabilities:` entry for those tags is ignored with one warning. `env.check` is ignored by that map the same way. `bolt env probe` and `bolt env ensure` select the handler by `checkId` instead of running every match. The other core tags (`vcs.sync`, `vcs.info`, `vcs.revision`, `artifact.store`) and plugin tags are singletons.

```yaml
# bolt.yaml — commit this
capabilities:
  vcs.sync: git/pull
  vcs.info: git/info
```

```yaml
# bolt.local.yaml — gitignored, optional. This key wins; other keys stay as in bolt.yaml.
capabilities:
  vcs.sync: svn/update
```

`capabilities: {}` is the same as leaving the key out. When only one built handler provides a tag, Bolt selects it and previews `(auto: only match)`. `bolt inspect` and `bolt run --dry-run` also show `(bolt.yaml)` or `(bolt.local.yaml)` for an explicit key. A task step can name the tag: `uses: vcs.sync`.

Several built handlers and no choice exits `3` with `CAPABILITY_AMBIGUOUS`. No handler exits `3` with `CAPABILITY_MISSING`. A ref that does not provide the tag exits `3` with `CAPABILITY_SELECTION_INVALID`. An unknown key or a bad ref exits `3` and names the file, the key, and a "did you mean" hint. Exit `2` is only for CLI usage errors. A selection that names a plugin which is not built asks you to run `bolt plugin build <namespace>` and does not use those three codes. `bolt inspect` and `bolt run --dry-run` resolve a built selection even when a sibling plugin is not built. `bolt run` still compiles every plugin, so a sibling that fails to compile can still fail the run.

Built-in `git/pull` and `svn/update` both provide `vcs.sync`. A project that keeps `uses: git/pull` does not need this map. No Unreal project is required to choose between git and svn.

`capabilitySelectionHash` is the digest `plan_hash` will take as `capability_selection` when BOLT-AI-2 lands. This release does not change `plan_hash`.

## Frozen

Plugin API v2 is frozen. Until a plugin API v3, which requires a bolt major version, this API is append-only. That includes the types in `bolt.d.ts`, this guide, and the [Plugin API](/api/plugin-api) page. Existing fields, hook signatures, and `HandlerResult.status` values keep their meaning. New optional fields may be added.

A plugin API v3 is required to remove or reinterpret an existing field, to make `emit` required with no transition, to change `HandlerResult.status`, or to change a hook signature incompatibly.

`bolt version --json` lists `2` in `plugin_api` and `plugin-api-2` in `capabilities`. It does not list a `config-hooks` capability. Config hooks are part of plugin API v2, not a separate capability flag.

A plugin written to this page keeps working on a bolt that lists `plugin-api-2`. A later bolt may add optional fields. It will not change the fields this page already describes without a plugin API v3.
