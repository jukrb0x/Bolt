Run tasks (in the order you type) or a single flow defined in `bolt.yaml`.

## Usage

```bash
bolt run <name...> [--dry-run | --simulate] [--key=value ...] [-- key=value ...]
bolt run --dry-run <name...> --json
bolt run <name...> --execute --plan=<plan_hash> [--confirmed-by-user] --json
```

## Description

`bolt run` is the one verb for executing work. A **task** is a named list of
steps; a **flow** is a named, ordered set of tasks. You pass names positionally:

- **Multiple tasks** — `bolt run update build start` runs each named task in the
  **exact order you typed**. There is no hidden reordering.
- **A single flow** — `bolt run daily` runs the flow's steps in order. A single
  name is treated as a flow only if it matches a flow; otherwise it must be a task.

If any name is neither a task nor a flow, the run fails before executing anything
with `Unknown task "<name>"` / `Unknown flow "<name>"` (exit code `2`), followed by the available tasks and flows.

Flows are **fail-fast**: the first failing task aborts the flow, unless that task
is listed in the flow's `continue_on_fail`.

## Parameters

Trailing `--key=value` flags are collected as params that apply to the **whole
run**. They shallow-override each step's `with:` values (params win), and are
available in interpolation as `${{ params.key }}`.

```bash
bolt run build --target=client      # override the build target
bolt run build --config=debug       # override the build configuration
```

**Config shorthand** for the `config` param: `dev` → `development`, `dbg` → `debug`, and `dbggame`/`DebugGame` → `debuggame`.

```bash
bolt run build --config=dev          # resolves to development
bolt run build_editor --config=debuggame # aliases: dbggame, DebugGame
```

### Strict argument parsing

`bolt run` rejects anything it does not understand, with exit code `2`, before
any step runs. Shared rules for every command are in [CLI Reference](/cli#invalid-flags).
Run-specific rules:

- Unknown flags, long or short (`--dryrun`, `-x`, `-xyz`). A close match is suggested.
- A value on a boolean flag (`--dry-run=false`).
- A param value that starts with `--` (`--extra=--verbose`).
- Flags before the command (`bolt --dry-run run deploy`). Flags go after the
  command: `bolt run deploy --dry-run`. Only `-h`, `--help`, and `--version`
  are allowed before it. A help flag wins (`bolt --help --version` shows help);
  otherwise `--version` must be used on its own (`bolt --version`) and takes no value.
- Reserved names: `dry-run`, `simulate`, `json`, `agent`, `execute`, `plan`,
  `confirmed-by-user`. On `bolt run` they are flags, not param names. Using one as a
  param (`-- plan=x`, or a valued form of a boolean such as `--execute=true`) fails
  with exit `2` and tells you to rename the param, e.g. `plan` → `my_plan`.
  `--json=v1` is accepted. `--plan=<hash>` is the plan hash flag. These combinations
  are usage errors: `--execute` with `--dry-run` or `--simulate`, `--simulate` in
  agent mode, `--execute` without `--plan`, `--plan` without `--execute`, and an
  empty `--plan`. Reserved names are case-sensitive: `--PLAN=x` is an ordinary param.
  The same names on other commands are still "not supported yet" unless that command
  declares them.
- `--dry-run=false` and `-- dry-run=false`: to run for real, just remove `--dry-run`
  (the same for `--simulate`).
- `--dry-run` together with `--simulate`.
- `help` with a value (in addition to the 7 reserved names above, handled
  separately): `--help=<value>` fails with `--help takes no value. Use: bolt run --help`,
  and `-- help=<value>` fails with `"help" cannot be used as a param name`. Both
  tell you to rename a `help` param, e.g. to `my_help`. Bare `--help` / `-h`
  still show help. This matches `--help=<value>` before the command
  (`bolt --help=1` fails with `--help takes no value`).
- Unknown names (`bolt run mrk`) fail with `Unknown task "mrk". Did you mean "mark"?`
  (or `Unknown flow "…"` when the closest match is a flow) and list the project's
  tasks and flows in declaration order. When the only match differs by case
  (`bolt run Mark` / `bolt run Build`), the message adds `Task names are case-sensitive.`
- No name (`bolt run`) prints the usage with the project's actual tasks and flows;
  outside a project it points to `bolt list` and `bolt init`.

A mistyped command (`bolt rn mark`) fails with exit code `2` and
`Unknown command "rn". Did you mean "run"?` plus the list of commands.
A mistyped global flag before the command (`bolt --verison`) suggests
`Did you mean "--version"?`.

Suggested commands in error messages quote values that contain spaces or shell
characters, so they can be copied as-is.

To pass a value that starts with `--` (for example a flag forwarded to an
external tool), put it after a bare `--` separator. Everything after `--` is
parsed only as `key=value` params:

```bash
bolt run build -- extra=--verbose
```

For tool flags that never change, prefer putting them in `bolt.yaml`
(`with:` or `vars`) instead of the command line.

## Dry run and simulate

`--dry-run` is a static preview. Bolt reads `bolt.yaml`, resolves the plan exactly
like [`bolt inspect`](/cli/inspect), and prints each step as `would run …`. Nothing
is executed:

- no `run:` commands, local actions, or child processes (not even `git` for notifications);
- no plugin is imported or compiled, `bun install` never runs, and no `onInit`,
  `onBeforeStep`, `onAfterStep`, or handler is called;
- no files are written: no `.bolt/` directory, no `.bolt/.cache`, no log file.

```text
$ bolt run build ship --dry-run
Dry run: showing what would run. Nothing is executed.
Config: /path/to/bolt.yaml
Tasks: build ship

>> build
  would run uses: ue/build  target=editor
    -> built-in plugin ue: handler not called in dry-run
>> ship
  would run uses: ./actions/upload  bucket=nightly
    -> local action: would execute ./actions/upload/run.sh with BOLT_INPUT_BUCKET=nightly
  would run uses: deploy/push
    -> project plugin .bolt/plugins/deploy: not loaded in dry-run; its handler and params are not validated (not an error)

Dry run complete.
Nothing was executed: no commands, plugins, hooks, or handlers ran, and no files were written.
To preview with plugin dry-run logic, hooks, and a log file, use --simulate.
```

What a dry run can check statically:

- every name, `call:` target, and interpolated value (`${{ params.* }}`, `vars`, `env`);
- built-in plugin handlers (`ue`, `fs`, `json`, `git`, `svn`) and their params;
- that a local action has an `action.yaml` and a run script;
- where a project or user plugin would be loaded from.

What it cannot show: the exact command a handler would build (for example the
`Build.bat` line from `ue/build`), and whether a project or user plugin accepts its
params. Use `--simulate` for that. Third-party plugin params are not validated and are
not an error. Config problems a real run would hit (unknown plugin namespace or op, bad
built-in params, missing action script) are marked with `!` and the dry run exits `3`.

The library API (`dryRun: true`) still behaves like `--simulate`: plugins load and hooks
run. A pure library dry run is tracked as BOLT-DX-3.

`--simulate` loads plugins and runs their hooks and handlers with `ctx.dryRun = true`.
Handlers that honor `ctx.dryRun` log what they would do instead of doing it.
`run:` steps and local actions are skipped (a missing `action.yaml` or run script still fails the step). Simulate writes a log file under
`.bolt/logs/`, may compile project plugins into `.bolt/.cache` or run `bun install`,
and a plugin can still have side effects. Notifications are not sent.
`--dry-run` and `--simulate` cannot be combined.

## Agent mode

Agent mode is on when any of these is set: `--agent`, `BOLT_AGENT` equal to `1` or `true` after trimming (any case), `--execute`, `--plan`, or `--confirmed-by-user`. On `bolt run` it prints one `bolt.run/v1` JSON document. A human run with none of those flags is unchanged.

`bolt run --dry-run <names> --json` (or the same command with `--agent` and no `--execute`) is a static preview. It returns `plan_hash`, effective `ai`, `ai_reasons`, and a `plan` object with the same shape as [`bolt inspect --json`](/cli/inspect). It does not import project or user plugins and writes nothing.

`bolt run <names> --execute --plan=<plan_hash> --json` recomputes that hash and runs the plan when both gates pass:

1. **Stage 1** does not import plugin code. It refuses with exit `4`, in order: `PLUGIN_NOT_BUILT`, artefact integrity (`PLAN_MISMATCH` plus `ai_reasons` code `ARTEFACT_TAMPERED`), `AGENT_EXECUTION_DISABLED` (`ai.run: never`), `PLAN_MISMATCH` (the hash differs), `AI_FORBIDDEN` (effective `ai` is `false`), `CONFIRM_REQUIRED` (effective `ai` is `confirm` and `--confirmed-by-user` is absent). Capability errors still exit `3` before this. No log is written.
2. **Stage 2** loads only the participating plugins, from their content-addressed artefacts. It does not compile or install. If the loaded handlers differ from the manifest, the run stops with `PLAN_MISMATCH` (exit `4`) and writes no log. Otherwise it executes the same plan.

A non-builtin `ai: true` handler is treated as `confirm` unless its namespace is in `ai.trust_plugins`. A plugin that shadows a built-in namespace is `ai: false` (`PLUGIN_SHADOWS_BUILTIN`). `--confirmed-by-user` lets a `confirm` plan run. Built-in confirm-tier handlers are signed off: builds, start, `generate_project`, setup, ini writes, svn and git updates, and file writes are `"confirm"`. Destructive built-ins stay `ai: false` (`ue/kill`, `ue/svn_revert`, `ue/svn_cleanup`, `ue/fix_dll`, `fs/delete`, and the stricter `ue/fillddc` and `ue/ini_remove`). Read-only built-ins an agent may run without that flag include `ue/diagnose_uat`, `ue/doctor_ddc`, `ue/info`, `ue/ini_get`, `ue/ini_read_all`, `git/info`, and `svn/info`. `bolt version --json` lists `confirm`.

`plan_hash` covers the resolved plan, including each task's `continueOnFailure` and the handler a capability step resolves to. Changing `continue_on_fail` or a `capabilities:` mapping changes the hash. `ue/ini_get` and `ue/ini_read_all` may only read a `file` inside the UE `project.path` (symlink-resolved). A path outside it is `AI_FORBIDDEN`. `--plan` without `=` is the same flag as `--plan=<hash>`.

Success data is `{ preview: false, plan_hash, outcome: "ok", log }`. A failed step is `outcome: "failed"` with error `RUN_FAILED` (exit `1`). The same envelope also lists that step's issue (`code`, `message`, optional `hint`, plus `ref` and `index`) so it matches `steps[].error` in the session file. A real execute writes `.bolt/sessions/<session_id>.json`. See [bolt session](/cli/session).

## Exit codes

| Code  | Meaning                                                                                                                                                                                                               |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`   | Success (a dry run with no problems, or an agent execute that finished)                                                                                                                                               |
| `1`   | Task failure (a step failed while running)                                                                                                                                                                            |
| `2`   | Usage error: unknown flag, command, task, or flow; malformed param; no task given; illegal agent-flag combination                                                                                                     |
| `3`   | Config error: `bolt.yaml` missing, unreadable, unparseable, failing the schema, an invalid task graph (unknown `call:` target, call cycle, malformed or legacy `uses:` ref), or a config problem found by `--dry-run` |
| `4`   | Denied: `PLUGIN_NOT_BUILT`, `PLAN_MISMATCH`, `AGENT_EXECUTION_DISABLED`, `AI_FORBIDDEN`, `CONFIRM_REQUIRED`. An unreadable `bolt.yaml` exits `3`                                                                      |
| `70`  | Internal: uncaught exception or rejection. JSON envelope when it can be written; `config` is null                                                                                                                     |
| `130` | Interrupted: `SIGINT`, or `SIGBREAK` on Windows                                                                                                                                                                       |

Config errors are reported before anything runs and before a log file is created.

## Options

| Flag                  | Default | Description                                                                   |
| --------------------- | ------- | ----------------------------------------------------------------------------- |
| `--dry-run`           | `false` | Show what would run; runs nothing, writes nothing                             |
| `--simulate`          | `false` | Run plugins in dry-run mode; may have side effects. Not allowed in agent mode |
| `--json`              | `false` | Print one `bolt.run/v1` document. With no `--execute`, this is a preview      |
| `--agent`             | `false` | Agent mode (also `BOLT_AGENT=1` or `true`). JSON preview unless `--execute`   |
| `--execute`           | `false` | Run a previewed plan. Requires `--plan`. Implies agent mode                   |
| `--plan=<plan_hash>`  | -       | Hash from a previous `--dry-run --json` preview. Requires `--execute`         |
| `--confirmed-by-user` | `false` | User approved a `confirm` plan. Implies agent mode                            |
| `--<key>=<value>`     | -       | Pass a param to the whole run (overrides `with:`)                             |
| `-- <key>=<value>`    | -       | Params after `--`; values may start with `--`                                 |

## Arguments

| Argument    | Required | Description                                   |
| ----------- | -------- | --------------------------------------------- |
| `<name...>` | Yes      | One or more task names, or a single flow name |

## Examples

```bash
# Run tasks in the typed order
bolt run update build start

# Run a predefined flow
bolt run daily

# Override a step's with: value for the whole run
bolt run build --target=client

# Build a specific configuration (shorthand)
bolt run build --config=dbg

# Preview the resolved steps without executing anything
bolt run update build --dry-run

# Let plugins show what they would do (hooks run, a log file is written)
bolt run update build --simulate

# Agent preview, then execute an ai:true plan (hash comes from the preview)
bolt run show_engine --dry-run --agent --json
bolt run show_engine --execute --plan=<plan_hash> --json
```

## Defining Tasks and Flows

Tasks and flows live in `bolt.yaml`. The three execution keys are `uses` for a
plugin/local action, `call` for a reusable task (cycle-detected), and `run` for a
shell command.

```yaml
tasks:
  kill: [{ uses: ue/kill }]
  update: [{ uses: ue/update_engine }, { uses: ue/update_project }]
  build: [{ uses: ue/build, with: { target: editor } }]
  build_editor: [{ call: build, with: { config: debuggame } }]
  start: [{ uses: ue/start }]

flows:
  daily:
    description: Update, build, and launch the editor
    steps: [update, build, start]
    continue_on_fail: [start] # update/build failures abort; start may fail
  reset:
    description: Kill, update, regenerate, rebuild
    steps: [kill, update, genproj, build]
    continue_on_fail: [kill] # kill may fail (nothing running) without aborting
```

<Note>
  **Migrating from v1?** `bolt go`, ops, and variants are gone. Replace `bolt go update build` with
  `bolt run update build`, and replace op variants (`build:client`) with params (`--target=client`).
  Legacy `uses: task/name` is rejected; replace it with `call: name`.
</Note>

Multi-task start notifications are sent once per invocation. They show the
top-level task list and each recursively owned action.
