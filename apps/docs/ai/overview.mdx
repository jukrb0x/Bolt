Coding agents such as Cursor and Claude Code use Bolt through the same `bolt` CLI that people use. A
**Bolt skill** tells the agent which commands to run and in what order. Planned: with `--json`, each
command will return one structured JSON document the agent can read without parsing human output. Today
only `bolt version --json` prints JSON.

Bolt does not run an MCP server or any other service for agents. There is one interface, the CLI, and
the same permissions and allowlists you already use for shell commands apply to it.

<Warning>
  **Status.** Most of this page describes a reviewed design for agent support, pending maintainer
  sign-off. It is not in the current release. Today's binary has the `ai` handler flag, `bolt ai`,
  and a first skill. It does not have `--json` (except `bolt version --json`), agent mode, `bolt
  status`, or `--execute`. Sections below marked **Planned** are not implemented yet.
</Warning>

## Available today

### The `ai` flag on handlers

Every plugin handler declares whether agents may use it. Plugin authors set this with
`@handler({ ai })` or `defineHandler({ ai })`. See the [Plugin API](/api/plugin-api) for details.

### `bolt ai`

[`bolt ai`](/reference/cli/ai) writes `.bolt/ai-context.md`: the project's tasks, flows, targets, and the
plugins and handlers an agent may use. Handlers that agents may not use are left out, and handlers that need
your confirmation are marked as such. The file header carries a context hash computed from `bolt.yaml` and
the plugin catalog. `bolt.local.yaml` is not an input. Use `bolt ai --stdout` to print it instead of
writing the file. Both forms load project and user plugins and run their top-level code, and a first run writes
plugin build caches under `.bolt/.cache/`.

### The current skill

The repository ships a skill at `skills/boltstack/SKILL.md`. It has the agent load `.bolt/ai-context.md`,
use only the tasks and flows listed there, preview with `--dry-run` first, ask before running `--simulate` or `kill`
tasks, respect fail-fast, and leave `bolt.yaml` and `bolt.local.yaml` alone.

<Note>
  `bolt run --dry-run` is a static preview. It reads `bolt.yaml`, resolves the plan, and prints each step
  as `would run …`. It does not load project or user plugins, call hooks or handlers, start processes, or
  write files. `bolt run --simulate` is different: it loads plugins and runs their hooks and handlers with
  `ctx.dryRun = true`, and may have side effects. Bolt does not prompt before `--simulate` runs, so the agent
  must ask you first; only let it run `--simulate` after you approve it. The two flags cannot be combined. See [bolt run](/cli/run).

Every command rejects unknown and reserved flags with exit code `2` before anything runs.
Unknown-flag errors may include did-you-mean and a `Flags:` / `--help` line; reserved errors
(e.g. `bolt list --json`) are only the "reserved by bolt and not supported yet. Remove it…"
line. Reserved names `--json`, `--agent`, `--execute`, `--plan`, and `--confirmed-by-user`
use that reserved wording unless the command declares them (`bolt version --json` works).
Undeclared `--dry-run` / `--simulate` on other commands are unknown flags, not reserved.
Reserved names cannot be used as task params on `run` / `inspect`. `bolt ai --json` does not
write `.bolt/ai-context.md`; it exits `2`. Planned agent commands therefore fail on today's
binary — wait until `bolt version --json` reports the capabilities.

</Note>

## Safety model

Available today: `bolt run --dry-run` is a static preview that runs no plugins, hooks, handlers, or
processes and writes no files. `bolt run --simulate` runs plugin code and is not a safe preview.

Planned: Bolt's checks will guard against a cooperative agent that makes mistakes: a wrong task name, a
plan that changed between preview and execution (bound by `plan_hash`), or a forgotten confirmation
(`--confirmed-by-user`). `bolt version --json` will advertise a `static-dry-run` capability; today it
lists only `handler-results`, `capability-tags`, and `plugin-api-2`.

Bolt will not be able to stop an agent that ignores the skill. It will not be able to verify that
`--confirmed-by-user` reflects a real yes, and it does not sandbox plugin code. The real boundary is your
agent client's command allowlist:

- Auto-allow `bolt version`, `bolt list`, `bolt info`, `bolt check`, `bolt inspect`, and only the prefix
  `bolt run --dry-run`. Add `bolt status` once it exists (Planned).
- Never auto-allow any other `bolt run`, `bolt plugin build`, `bolt self-update`, `bolt init`,
  `bolt migrate`, or any `bolt ai`. `bolt ai --json` exits `2` and writes nothing. Never auto-allow
  `bolt run --simulate` or `bolt ai --stdout`: both run plugin code from the repository.
- On Windows, write rules with the absolute path `%USERPROFILE%\.bolt\bin\bolt.exe` so a `bolt.cmd` or
  `bolt.exe` in the repository cannot take its place.
- Planned: once `bolt version --json` lists the `static-dry-run` capability, check for it before
  allowlisting `bolt run --dry-run`.

## Planned: skills that call the CLI with `--json`

Nothing in this section is implemented in the current release unless it says so. There is no
`bolt status` command, and `--json` exists only on `bolt version`.

### The loop (Planned)

<Info>
  Only the first half of step 1 works today: `bolt version --json` prints `version`, `plugin_api`,
  `manifest_format`, and `capabilities`. Steps 2 to 5 (`bolt status`, `--agent`, `--json` on other
  commands, `plan_hash`, `--execute`, `--plan`, `--confirmed-by-user`) are not implemented.
</Info>

An agent following the Bolt skill works in five steps:

<Steps>
  <Step title="Check capabilities">
    `bolt version --json` returns the binary's version and a list of capabilities. The skill decides what
    it may do from the capabilities, never from the version number. A binary that prints plain text has
    no capabilities, so the agent stays read-only and hands commands to you.
  </Step>
  <Step title="Discover">
    `bolt status --agent --json` reports setup and policy. `bolt list --agent --json` and
    `bolt info --agent --json` return tasks, flows, plugins, and targets. The agent picks names only from
    this output.
  </Step>
  <Step title="Preview">
    `bolt run --dry-run <names…> [--key=value] --agent --json` resolves the plan without running anything.
    It returns the steps, whether an agent may run the plan, and a `plan_hash`.
  </Step>
  <Step title="Confirm">
    If the plan needs confirmation, the agent shows you the plan and asks. If agents may not run it, the
    agent gives you the command to run yourself.
  </Step>
  <Step title="Execute">
    `bolt run <same names and params> --execute --plan=<plan_hash> --agent --json`, plus
    `--confirmed-by-user` after you said yes. Bolt re-resolves the plan and refuses if it no longer
    matches the hash.
  </Step>
</Steps>

### JSON output (Planned)

<Info>
  The shared envelope, per-command schemas, and `«env:NAME»` / `«local:NAME»` redaction are not
  implemented. `bolt version --json` prints its own flat object, not this envelope.
</Info>

With `--json`, stdout carries exactly one JSON document. Logs go to stderr. Every document has the same
envelope:

```json
{
  "schema": "bolt.inspect/v1",
  "bolt": "x.y.z",
  "ok": true,
  "config": { "path": "D:/Work/MyGame/bolt.yaml", "local": "D:/Work/MyGame/bolt.local.yaml" },
  "data": {},
  "warnings": [],
  "errors": []
}
```

- `ok` is `false` exactly when the exit code is non-zero. Errors carry a stable `code`, and agents
  branch on the code and exit status, not on message text.
- Each command has a versioned schema (`bolt.list/v1`, `bolt.inspect/v1`, `bolt.run/v1`, …). Within
  `v1`, changes are additive only.
- Values from environment variables appear as `«env:NAME»`, and values set in `bolt.local.yaml` appear
  as `«local:NAME»`. This keeps secrets out of agent transcripts. It does not hide them from an agent
  that can read your files.

Planned `--json` support: `version`, `list`, `info`, `check`, `inspect`, `status` (new), `run`, and `ai`.

### Which plans an agent may run (Planned)

<Info>
  Effective agent mode per plan and the `bolt.local.yaml` switch are not implemented. Today the `ai`
  flag only controls what `bolt ai` writes to `.bolt/ai-context.md`.
</Info>

Each plan gets an effective agent mode derived from its steps, and the strictest step wins. Shell
(`run:`) steps, local actions, and handlers from non-built-in plugins always require your confirmation.
You will be able to turn off agent execution on a machine in `bolt.local.yaml`. The exact rules and
built-in handler defaults are still being finalized.
