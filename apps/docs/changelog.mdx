## Unreleased

### Local observation on bolt dash

`bolt dash` is a local observer for one project's execute sessions. It listens on `127.0.0.1` only. It is not CI, Jenkins, or GitHub Actions.

Compared with the A3b dashboard, this adds three things:

- **Plan vs execute.** An execute session's detail row lines up the plan node with that step's status. The plan node is `steps[].node` from the session file. `steps[].ref`, `steps[].status`, and `steps[].error` stay the execution side. If `node` is missing, the page reads `GET /sessions/<session_id>/plan` (`bolt.inspect/v1`) for those task names. That read does not run the plan, and it does not put a dry-run or preview record on the default session list.
- **Refresh while running.** The page polls the existing list and detail reads while a session is `running` and the tab is visible. A finished, failed, or interrupted session stops the poll. Hiding the tab stops it. The server does not invent the next step.
- **Log drawer.** A session's `log_run_id` opens a truncated tail of `.bolt/logs/<log_run_id>.log`. The id has to match the session-id character set, and `..` or an absolute path is rejected. Secret flag values are masked. With no `log_run_id`, the drawer says the log cannot be linked. The log is not the source of `steps[].error.code`.

### Local session dashboard

`bolt dash` serves a readonly page on `127.0.0.1` only. The OS picks a free port unless you pass `--port`. It prints the URL and stops on Ctrl+C. The page lists this project's execute sessions, the same set as `bolt session list`. A session detail shows the step graph from `steps[]`. The stuck panel shows that step's `error.code`, `error.message`, and `error.hint`.

`GET /sessions` is one `bolt.session.list/v1` document. `GET /sessions/<session_id>` is one `bolt.session/v1` document, including a preview record that the list hides. The page does not run `bolt run --execute` and does not write sessions except the reclaim those reads already do. It is a local observer, not CI, and it does not listen on `0.0.0.0`.

### Run sessions

`bolt run` writes `.bolt/sessions/<session_id>.json` when it actually executes a plan. That includes a human `bolt run <task>` and `bolt run <task> --execute`. Dry-run, JSON preview, and `--simulate` do not write a session. The directory is under `.bolt/`, which is already gitignored.

`bolt session list` prints those execute sessions. `bolt session list --json` is one `bolt.session.list/v1` document. `bolt session show <session_id>` prints one session, including a `preview` record that list hides. `bolt session show --json` is `bolt.session/v1`. `bolt session clear` deletes the session files. `bolt session clear --json` is `bolt.session.clear/v1`. The envelope matches the other commands.

A session is `running` until the run finishes `ok` or `failed`, or a catchable interrupt writes `interrupted`. `list`, `show`, and `bolt dash` reclaim a `running` session when its pid is gone, or when it has no pid and the file is older than 2 hours. There is no `stale` status. Files older than 7 days are removed on those reads, except a `running` session whose pid is still alive.

A failed step stores `{ code, message, hint? }` from the runner. On `bolt run --execute --json`, that same issue is also in `errors` with `ref` and `index`. `errors[0]` stays `RUN_FAILED`. `invocation.argv_summary` masks token, password, key, and secret flag values and does not store the raw argv. `steps[].result` is the handler's public fields only.

### Environment manifest and empty-shell rejection

`bolt env manifest` prints the effective environment manifest. Checks come from `env.checks` in `bolt.yaml`, from the file named by `env.manifest`, or from `--manifest`. That path is relative to the project root. The source rules match `bolt env probe`. `--json` prints one `bolt.env.manifest/v1` document. `data` is `source`, `checks_declared`, and `checks` (each check is `id`, `require`, and `version` or `params` when set). These are declarations, not probe results.

A project with no `env` key, or with an empty check list, exits 0 with warning `ENV_NO_MANIFEST`. A drive letter, an absolute path, or a path that leaves the project root exits 3 with `MANIFEST_INVALID`. `bolt status --json` still lists `schemas.env` as `v1`.

`bolt env ensure` refuses an empty shell. A handler marked `studioSetupShell: true` (manifest field `studio_setup_shell`) exits 2 with `EMPTY_SHELL` and is not called. A probe result without `current` and `expected`, or an ensure result without boolean `data.changed`, is the same refusal. A handler that returns `data.changed` true or false is kept, including one that calls an installer and then reports a noop. `ue/setup` is unchanged. It is a UE plugin step, not this refusal, and not the platform environment contract.

`data.plan` on ensure is the environment plan. It is not a workspace sync plan. `bolt workspace sync` stays removed.

`bolt check` warns when a project has no `env` block and a task is a single `run` of a setup script (`*.ps1`, `*.bat`, `*.cmd`, or `*.sh`). The message starts with `ENV_SETUP_SHELL`. The command still exits 0. A task that uses `ue/setup`, or a task with more than one step, does not warn. The warning does not stop `bolt run`.

`defineHandler` and `@handler` accept optional `studioSetupShell`. That field is additive on plugin API v2. The handler signature is unchanged.

This is not a one-click environment. `--strict` is not in this slice.

### Environment ensure

`bolt env ensure --dry-run` prints a fill-gaps plan and a `plan_hash` (`sha256:` plus 64 hex characters). It does not change the machine. `changed`, `noop`, and `failed` are empty. `--json` prints one `bolt.env.ensure/v1` document. The envelope matches probe.

`data.plan` is the environment plan. Each row is a declared check id with `action` `ensure` or `noop`. That plan is not a workspace sync plan. `bolt workspace sync` stays removed. `ue/setup` is unchanged and is not this command.

`bolt env ensure --execute --plan=<plan_hash> --confirmed-by-user` applies the plan. The hash must match a fresh dry-run. A different hash exits 4 with `PLAN_MISMATCH`. Missing `--confirmed-by-user` exits 4 with `CONFIRM_REQUIRED`. Neither refusal changes the machine.

Ensure only acts on required gaps (`will_change: true`). `require: false` is `noop` with reason `not_required`. A check that already passes is `noop` with reason `already_satisfied`. After execute, `changed` lists the ids that were filled, `noop` lists the rest with a reason, and `failed` lists `{ id, code }` when one check could not be filled. A second ensure, with nothing broken in between, reports `summary.changed` 0.

The built-in git plugin provides `vcs.git.lfs` (probe and ensure). Ensure runs `git lfs install --skip-repo` only when the Git LFS binary is new enough and the user filters are missing. It does not install the Git LFS package. The test checks `fixture.tool.a` and `fixture.tool.b` can write a marker file when ensure runs. This is not a one-click environment.

`ctx.envCheck.action` is `"ensure"` only on that apply step. Probe leaves it unset. The handler signature is unchanged.

Not in the ensure slice: `EMPTY_SHELL` rejection and a standalone `bolt env manifest` command (both are in the section above), and `--strict`.

### Environment probe

`bolt env probe` reads declared environment checks and prints what is missing. It does not install tools. Filling gaps is `bolt env ensure`. `ue/setup` is unchanged.

Checks live in `bolt.yaml` under `env.checks`, or in a file named by `env.manifest` or `--manifest`. That path is relative to the project root. A drive letter, an absolute path, or a path that leaves the project root exits 3 with `MANIFEST_INVALID`.

`--json` prints one `bolt.env.probe/v1` document. The envelope matches the other commands. `data.manifest` is the effective list (`source`, `checks_declared`). `data.checks` is every result. `data.gaps` is the fail and warn rows (`id`, `status`, `current`, `expected`, `fix`). A gap does not change the exit code.

A project with no `env` key, or with an empty check list, exits 0 with warning `ENV_NO_MANIFEST`, `checks: []`, and `gaps: []`. A declared id that no plugin provides exits 3 with `CHECK_UNKNOWN` in `errors`. That id is not reported as a pass.

Plugins contribute a check with capability `env.check` and a stable `checkId`. Core finds handlers with `findByCapability("env.check")` and calls the one whose `checkId` matches. The handler sees the declaration on `ctx.envCheck` (`id`, `require`, and `version` and `params` when set). `require: false` reports a failing check as `warn`. A `capabilities:` entry for `env.check` is ignored with one warning. It does not select a single handler.

`bolt status --json` lists `schemas.env` as `v1`.

Not in the probe slice: a standalone `bolt env manifest` command (it is in the section above), and `--strict`. Ensure is the separate command above.

### Workspace sync command removed

`bolt workspace sync` is removed, including `--dry-run` and `--json`. Invoking it is an unknown command. It does not print a plan. `bolt status --json` does not list `schemas.workspace`. Daily multi-repo update stays pipeline + `vcs.sync`.

`workspace.roots` is unchanged. `bolt list` and `bolt check` still read that inventory.

### Workspace roots inventory

`workspace` in `bolt.yaml` is a roots inventory. `bolt list` and `bolt check` read it. They do not update a working copy.

`workspace.roots` stays in declaration order. Each root requires `id`, `path`, and `role` (`engine`, `project`, or `related`). `path` is relative to the directory that contains `bolt.yaml`, or absolute. `bolt.local.yaml` does not override `path`. `vcs` is optional. Omit it when the root has none. `bolt list` and `bolt check` do not call it.

`bolt list` prints the roots. `bolt list --json` stays `bolt.list/v1` and adds `data.workspace.roots` when the block is present. Each root is `id`, `path`, `role`, `exists`, and `vcs` when that key is set. A path that is not on disk stays in the list with `exists: false`. `bolt check --json` reports the same inventory under `data.workspace` and warns `path does not exist`. That warning does not create the directory.

`sync_policy` and `pin` are not accepted. A file that still contains `sync_policy` fails validation (exit 3, `WORKSPACE_INVALID`). The hint is: remove `sync_policy`. Daily multi-repo update stays pipeline + `vcs.sync`. An empty `id` or `path`, a `role` outside the three names, or a duplicate root `id` is the same config error.

Not in this slice: a sync, a plan, or a `bolt workspace list` command.

### Workspace dry-run plan

Historical record of the removed dry-run command. Not a supported product path. Daily multi-repo update stays pipeline + `vcs.sync`.

`bolt workspace sync --dry-run` read an optional `workspace` block in `bolt.yaml` and printed a plan. It did not update a working copy. That slice did not sync mixed roots, and it did not add `bolt workspace status`.

`--json` printed one `bolt.workspace.sync/v1` document. The envelope matched the other commands (`schema`, `bolt`, `ok`, `config`, `data`, `warnings`, `errors`). `ok` was true exactly when the process exited 0. `bolt status --json` listed `schemas.workspace` as `v1`. That schema entry is removed with the command.

`workspace.roots` was kept in declaration order. Each root had `id`, `path`, `role` (`engine`, `project`, or `related`), `vcs`, and optional `pin` (a non-empty string, or `null`). `path` was relative to the directory that contains `bolt.yaml`, or absolute. `bolt.local.yaml` did not override `path`.

`sync_policy` accepted `one-side-safe`, `together`, and `pin-rev`. The frozen name was `one-side-safe`. That field is rejected. Remove it.

Dry-run `data` was `{ policy, plan }`. Each plan row was `{ root, action, target_rev, will_touch }`. Human output used those names as the table columns. `pin-rev` omitted a root that had no `pin`. Core only aggregated rows. The row came from a plugin handler tagged `vcs.revision` whose namespace equaled that root's `vcs`. Built-in `git` and `svn` did not provide that handler, so a config that relied on them exited 1 with `VCS_REVISION`. A plan row in tests came from a fixture plugin. `will_touch` was whatever that handler returned. That slice did not pre-check `together`, and it did not freeze later roots after a failure.

Without `--dry-run`, the command exited 2 with `USAGE` and did not sync.

These config errors exited 3:

- `WORKSPACE_INVALID` — the `workspace` block was missing or malformed, including a duplicate root id.
- `ROOT_MISSING` — a root `path` did not exist. The message named the root `id` and the path.
- `POLICY_UNKNOWN` — `sync_policy` was not one of the three names above.

Not in that slice: performing the sync, `touched` / `frozen` / `failed`, `bolt workspace status`, path overrides in `bolt.local.yaml`, and empty-shell rejection.

### doctor and why

`bolt doctor` and `bolt why` fan out the existing `doctor` and `diagnose` capability tags. This slice does not add a capability tag. It does not run a package step.

Both commands print one JSON document when `--json` is set: `bolt.doctor/v1` or `bolt.why/v1`. The envelope fields match the other commands (`schema`, `bolt`, `ok`, `config`, `data`, `warnings`, `errors`). `ok` is true exactly when the process exits 0. `bolt status --json` lists `schemas.doctor` and `schemas.why` as `v1`.

`bolt doctor` runs every built handler tagged `doctor`. A `capabilities:` entry for `doctor` (or any other fan-out tag in that map) warns once with `CAPABILITY_WARNING` and does not select a single handler. Every match still runs. Order is built-in list order, then `plugins[]` order, then any other built handler by ref. Core reads `data.checks` when the handler sets it, and otherwise maps `diagnostics[]` (`code` becomes `id`; there is no `pass` row on that path). Core sets `source` to `namespace/handler` and counts `summary` from `checks[].level`. A check with no usable `level` counts as `error` and adds warning `DOCTOR_CHECK_LEVEL`.

`data.checks[].level` is `pass`, `info`, `warn`, or `error`. Those results stay in `data` and the exit stays 0, including when a handler returns `status: "fail"`. `--fix` does not edit files. It exits 1 with `DOCTOR_FAILED` only when `summary.error` is greater than 0. `--only=<id>` keeps a check whose id is equal, or whose id starts with that text plus a dot (`ue.ddc` matches `ue.ddc.installed_vs_source` and does not match `ue.ddcfoo`). An `--only` filter that matches nothing warns `DOCTOR_ONLY_UNKNOWN`, returns `checks: []`, and still exits 0 even with `--fix`. No built `doctor` handler warns `DOCTOR_NO_PROVIDERS` and exits 0. A handler that throws exits 1 with `RUN_FAILED`.

`bolt why [run-id]` resolves a log, then runs every built `diagnose` handler. It does not print the log file. Diagnose handlers receive string params `log` (absolute path), `kind` (`run` or `explicit`), and `run_id` when one is known. Typed context fields for those values are not part of this slice. Core copies `diagnostics[]` (`level`, `fix`, and `source`) and sets `primary` to the first `level: "error"` item, otherwise the first item, otherwise `null`. The same fan-out order and `capabilities:` warning apply to `diagnose`. A handler `status: "fail"` stays in `data` and does not by itself exit 1.

Log source order:

1. `--log=<path>` — path relative to the current directory. `data.log.kind` is `explicit`. `run_id` is set only when that file is a `bolt_*.log` under the project's `.bolt/logs`.
2. The positional run id — a file under `<project>/.bolt/logs`, in this order: `<id>`, `<id>.log`, `bolt_<id>.log`. The id cannot contain a slash or `..`.
3. The newest failed run — `bolt_*.log` names in that directory, newest name first, whose text contains a line `<< <step>: FAILED (`.

If none of those yield a file, the command does not call plugins. It exits 1 with `WHY_NO_SOURCE` and `data.log: null`. A resolved log with no built `diagnose` handler exits 0 with warning `WHY_NO_PROVIDERS`, `diagnostics: []`, and `primary: null`. `--fail` does not edit the log. It exits 1 with `WHY_FAILED` only when some diagnostic is `level: "error"`. Warn and info diagnostics stay exit 0.

`ue/doctor_ddc` is a read-only `doctor` handler (`ai: true`). It reads `<project>/Config/DefaultEngine.ini` from the `ue` plugin config. An engine tree that contains `Engine/Build/InstalledBuild.txt` is installed; otherwise it is source. The check id is `ue.ddc.installed_vs_source`. If the ini sets a DDC graph only in the section the other flavor reads, the check is `level: "error"` with a non-empty `fix`. Moving that graph into the section this flavor reads makes the same check `pass`. With no `ue` config the handler skips and adds no check. It does not write the ini. `ue/doctor_toolchain` is not in this slice.

`ue/diagnose_uat` is a read-only `diagnose` handler (`ai: true`). It reads the log path `bolt why` already passes (`log`, plus `kind` and `run_id` when known) and does not need `ue` plugin config. One diagnostic is returned when the log is a UAT or Cook failure. A missing package, a shader compiler error, another `LogCook` error, or a fatal or assertion with a file and line becomes `primary`: a `code`, a short `message`, and a `fix`. The message is that cause. It is not the raw log, and a line that only says `Error:` is ignored. `Unknown Cook Failure` and `Error_UnknownCookFailure` are the AutomationTool wrapper. When a cause sits above that wrapper, the cause is the diagnostic. When the wrapper is the only cook signal, the code is `UE_COOK_UNKNOWN_ROOTCAUSE`. A log with no cook signal adds no diagnostic. This does not cook, package, or write a new failure log. Recent-failed-run lookup is unchanged: the newest `bolt_*.log` under `.bolt/logs` whose text contains `<< <step>: FAILED (`.

### Plugin API v2 freeze

Plugin API v2 is frozen. Until a plugin API v3 and a bolt major version, the public surface is append-only: `bolt.d.ts`, the plugin API page, and the migrating guide. Existing fields, hook signatures, and `HandlerResult.status` values keep their meaning. New optional fields may be added. Removing a field, changing what a field means, making `emit` required with no transition, changing `HandlerResult.status`, or changing a hook signature incompatibly requires plugin API v3.

`bolt version --json` still lists `plugin_api` values `1` and `2` and the capability `plugin-api-2`. It does not list `config-hooks`. Config hooks stay part of plugin API v2.

Core JSON Schema treats every `plugins[].config` value, and every `bolt.local.yaml` plugin override, as an opaque object. Plugin-specific shapes are no longer part of the core schema. Each plugin still validates its own config with its `metadata` schema and `validateConfig`. Build-configuration names used by the `ue` plugin live with that plugin.

### Plugin config hooks

`validateConfig` runs from `loadConfig` and `bolt check` after the core schema succeeds. Bolt calls it on every built-in, even when `bolt.yaml` has no entry for that plugin, and on every external plugin that config loaded. A plugin `metadata` Zod schema is checked only when that namespace has a `plugins` entry. Rules about tasks and other fields belong in `validateConfig`.

Config failures from this path exit 3:

- `CONFIG_PLUGIN_INVALID` — the metadata schema failed. The path is `plugins.<namespace>.config…`.
- `CONFIG_PLUGIN_REQUIRED` — a task uses `namespace/handler` and that plugin is not available. The `ue` plugin asks for `engine`, `project`, and `uproject` when a task uses `ue/…` and `plugins` has no `ue` entry. Any other missing namespace uses the hint `Add a plugins entry for "<namespace>" or install the plugin.`
- `CONFIG_PLUGIN_HOOK` — `validateConfig` threw or did not return `ConfigIssue[]`.

`aiContext`, `aiPathRoots`, and `initDetect` are part of the plugin API v2 types. `bolt init` does not call `initDetect`. Hooks require `apiVersion` 2. Bolt still calls a hook when the method exists. `bolt check` warns `Set apiVersion = 2 on plugin <namespace>` when a hook is present without plugin API v2.

`bolt ai` appends each plugin's `aiContext().markdown` after the plugin catalog. `bolt info --json` shallow-merges each plugin's `aiContext().info` into `data` (`Object.assign`). A missing or empty `info` is skipped. The same key later in the list replaces the earlier value. Order is built-ins, then `plugins[]` path plugins. `targets` is present only when a plugin contributes it. The core AI tagline does not name an engine. `bolt info` still does not import an unbuilt path plugin.

The `ue` and `svn` built-ins declare plugin API v2.

### Confirm gate (BOLT-M1 Phase 2b)

Built-in handler `ai` flags are signed off. Read-only handlers stay `ai: true`: `ue/info`, `ue/ini_get`, `ue/ini_read_all`, `git/info`, `svn/info`. There is no JSON read handler. These move to `"confirm"`: `ue/build`, `ue/build_engine`, `ue/build_program`, `ue/start`, `ue/generate_project`, `ue/setup`, `ue/update_engine`, `ue/update_project`, `ue/ini_set`, `ue/ini_override`, `git/pull`, `svn/update`, `fs/copy`, `fs/move`, `fs/mkdir`, `json/set`, `json/merge`. `git/status` and `svn/status` stay `"confirm"`. These stay `false`: `ue/kill`, `ue/svn_revert`, `ue/svn_cleanup`, `ue/fix_dll`, `ue/fillddc` (runs the editor to fill the DDC; stricter than confirm), `ue/ini_remove` (deletes a key), `fs/delete`, `git/checkout`, `git/clone`, `svn/cleanup`, `svn/revert`, `svn/commit`, `svn/add`. That changes `.bolt/ai-context.md` and its context hash. Run `bolt ai` again.

`bolt.local.yaml` `ai.run: never` refuses every agent-mode execute with `AGENT_EXECUTION_DISABLED` (exit 4), including a `"confirm"` plan that passes `--confirmed-by-user`. Omitted `ai.run` means `confirm` and does not block an `ai: true` plan. A `"confirm"` plan without `--confirmed-by-user` is `CONFIRM_REQUIRED` (exit 4). The hint is `Re-run with --confirmed-by-user after the user approves.` A human `bolt run` with none of `--json`, `--agent`, `--execute`, `--plan`, or `--confirmed-by-user` is still the text path and ignores `ai.run`.

`bolt version --json` appends the capability `confirm` after `agent` and `execute`. It does not remove those. The official skill may execute: `ai: true` when `agent` and `execute` are listed, and `"confirm"` only when `confirm` is listed and the user has approved that plan. It must not skip confirmation. Client allowlists must still not auto-allow `--execute` or `--confirmed-by-user`.

`bolt ai --json` prints one `bolt.catalog/v1` document and does not write `.bolt/ai-context.md`. `data.plugins` is the catalog (handlers with `ai: false` omitted). `--json` with `--stdout` is `USAGE` (exit 2). A missing or stale `bolt.plugin.json` is `CONFIG_INVALID` (exit 3) with hint `bolt plugin build <ns>`. `bolt status --json` lists `schemas.ai` as `v1`.

Not in this release: MCP, NDJSON, doctor/why, HMAC `plan_hash`, Unity, p4, and moving git and svn calls out of the `ue` plugin.

### Agent execute (BOLT-M1 Phase 2a)

`bolt run` accepts `--agent`, `--json`, `--execute`, `--plan=<plan_hash>`, and `--confirmed-by-user`. `--agent` is also on when `BOLT_AGENT` is `1` or `true` after trimming (any case). `--execute`, `--plan`, and `--confirmed-by-user` imply agent mode even without `--agent`. On `bolt run`, agent mode prints JSON. A human `bolt run` with none of those flags is unchanged, including a text `--dry-run`.

`bolt run --dry-run … --json` prints one `bolt.run/v1` document. `data` is `{ preview: true, plan_hash, ai, ai_reasons, plan }`. `plan` matches `bolt inspect --json` (`kind`, `name`, `names`, `params`, `context_hash`, `plan_hash`, `ai`, `ai_reasons`, `tasks`, `capabilities`). The same preview is what agent mode returns when `--execute` is absent.

`bolt run <names> --execute --plan=<plan_hash> --json` recomputes the hash and runs that plan when both gates pass. Success `data` is `{ preview: false, plan_hash, outcome: "ok", log }` (`log` uses forward slashes). A step failure is `outcome: "failed"`, with optional `failed_task` and `log`, error `RUN_FAILED`, exit 1. A bare `--plan` (no `=`) is agent mode and prints JSON, the same as `--plan=<hash>`.

`plan_hash` now also includes each task's `continueOnFailure` (the flow's `continue_on_fail` flag) and, when a step names a capability, the resolved `namespace/handler`. Phase 1b hashed neither. A `plan_hash` saved from Phase 1b, or from an earlier Phase 2a build, no longer matches. Preview again. That invalidation is expected.

An agent execute of `ue/ini_get` or `ue/ini_read_all` confines `file` to the UE plugin's `project.path`, after resolving symlinks. A path that leaves that directory, or that cannot be resolved, is `AI_FORBIDDEN`. The root is the UE project directory, not the directory that contains `bolt.yaml`. A human `bolt run` is not confined here.

Stage 1 does not import plugin code. It refuses with exit 4, in this order:

1. `PLUGIN_NOT_BUILT` — a participating non-builtin is not built. Hint: `bolt plugin build <ns>`.
2. Artefact integrity — the content-addressed file is missing or its bytes no longer hash to the manifest. `PLAN_MISMATCH`, and `ai_reasons` includes `ARTEFACT_TAMPERED`.
3. `AGENT_EXECUTION_DISABLED` — `bolt.local.yaml` has `ai.run: never`.
4. `PLAN_MISMATCH` — `--plan` is not the recomputed `plan_hash`.
5. `AI_FORBIDDEN` — effective `ai` is `false`. The hint is the human `bolt run …` command.
6. `CONFIRM_REQUIRED` — effective `ai` is `confirm` and `--confirmed-by-user` was not passed.

Capability errors still exit 3 before Stage 1. A Stage 1 refusal writes no log.

Stage 2 loads only the participating plugins, and only from the content-addressed artefact. It does not compile, install, or read the plugin source tree. If the live handlers, `ai`, or params schema hash differ from the manifest, the run stops with `PLAN_MISMATCH` (exit 4) and writes no log. Importing the artefact runs module top-level and a class constructor; `onInit`, hooks, and handlers run only after that check passes.

A non-builtin handler declared `ai: true` is capped at `confirm` unless its namespace is in `bolt.local.yaml` `ai.trust_plugins`. Trust does not lift `ai: false`. A plugin that shadows a built-in namespace is `ai: false`, with warning `PLUGIN_SHADOWS_BUILTIN`. `bolt inspect --json` uses the same effective `ai`, so the hash matches `bolt run`.

`--confirmed-by-user` is a mechanical check: a `confirm` plan runs when the flag is present. This release does not review built-in confirm-tier handlers, and `bolt version --json` does not advertise a `confirm` capability. Destructive built-ins stay `ai: false`. Read-only built-ins marked `ai: true` here: `ue/info`, `ue/ini_get`, `ue/ini_read_all`, plus the existing `git/info` and `svn/info`. `git/status` and `svn/status` stay `confirm`.

`bolt version --json` appends capabilities `agent` and `execute`. `bolt status --json` lists `schemas.run` as `v1`. `agent_mode` follows `BOLT_AGENT`. `bolt status` does not accept `--agent`.

Exit `70` is `INTERNAL` (uncaught exception or rejection). Exit `130` is `INTERRUPTED` (`SIGINT`, and `SIGBREAK` on Windows). Both try to print a JSON envelope with `config: null`.

Not in this release: Phase 2b confirm-tier sign-off, `bolt ai --json`, MCP, NDJSON, doctor/why, and HMAC `plan_hash`. The shipped skill still has no execute path.

These combinations exit 2: `--execute` with `--dry-run` or `--simulate`, `--simulate` in agent mode, `--execute` without `--plan`, `--plan` without `--execute`, and an empty `--plan`. `--json=v1` is accepted on `bolt run`.

### Content-addressed plugin builds (BOLT-M1 Phase 1b)

`bolt plugin build [namespace...] [--user] [--prune]` bundles TypeScript and JavaScript with the host bundler. The only host externals are `boltstack` and `zod`. It writes two caches:

- `<cache>/plugins/<ns>/artefacts/<artefact_hash>/index.js` — immutable bundle
- `<cache>/plugins/<ns>/manifests/<source_hash>-<config_hash>.json` — `bolt.plugin-manifest/v1`

Project plugins use `<project>/.bolt/.cache`. User plugins use `~/.bolt/.cache`. The command still writes `<plugin-root>/bolt.plugin.json`. A class plugin with a non-empty config gets one manifest per config hash, so two configs of the same source coexist. Function and object plugins, and class plugins with an empty config, use the config key `noconfig`.

A native `.node` addon, or a dynamic non-literal `require` or `import`, fails closed. The command exits 1 and writes no manifest and no `bolt.plugin.json` for that source and config. A human `bolt run` can still load that plugin on the existing unbundled path.

A human `bolt run`, and `bolt run --simulate`, keep today's compile-and-load path and also refresh the manifest and artefact for each non-builtin plugin they loaded. `bolt run --dry-run`, `bolt inspect`, `bolt list`, `bolt info`, `bolt check`, `bolt ai`, and `bolt status` do not import an unbuilt plugin and do not write the cache. `--prune` drops manifests whose source hash is not the one just built, and artefacts no remaining manifest names.

`bolt inspect --json` stays `bolt.inspect/v1`. It adds `data.names`, `data.context_hash`, `data.plan_hash`, `data.ai`, `data.ai_reasons`, and per-task `ai`. Human inspect text is unchanged and still shows real interpolated values. In JSON, `${{ env.NAME }}` renders as `«env:NAME»`. A value that comes from `bolt.local.yaml` renders as `«local:NAME»` (plugin-config leaves use a dotted path such as `«local:plugins.ue.engine.path»`). Execution still uses the real values. `plan_hash` is the sha256 of a canonical payload. A masked value contributes `sha256(value)` and never the plaintext. An unbuilt non-builtin plugin used by the preview is a warning `PLUGIN_NOT_BUILT` (exit 0) with hint `bolt plugin build <ns>`. That handler is treated as `ai: false` for the plan. This release does not fail the preview with exit 4.

`bolt info --json` adds masked `vars`, `targets`, and `plugins` (including plugin config).

`bolt status` and `bolt status --json` (`bolt.status/v1`) report `agent_mode` (always `false` in this release), context freshness, whether `bolt.local.yaml` is present and valid, whether each discovered plugin is built for the current source and config, `policy.ai_run`, and schema names. `data.schemas` lists only commands that accept `--json` today (`list`, `info`, `check`, `inspect`, `status`). It does not include `run` until `bolt run --json` exists.

`bolt.local.yaml` accepts `ai.run: never | confirm`. Omitted means `confirm`. `bolt status` reports it. It does not gate execution.

`bolt version --json` appends the capability `plugin-manifest`.

This slice does not add `--agent`, `--execute`, `--plan`, `--confirmed-by-user`, `bolt run --json`, or `bolt ai --json`.

### JSON envelope for read commands (BOLT-M1 slice 1a)

`bolt list`, `bolt info`, `bolt check`, and `bolt inspect` accept `--json`. Stdout is one JSON document and nothing else. `console.log` and other stdout writes are redirected to stderr for that process.

```json
{
  "schema": "bolt.list/v1",
  "bolt": "x.y.z",
  "ok": true,
  "config": { "path": "/abs/bolt.yaml", "local": null },
  "data": {},
  "warnings": [],
  "errors": []
}
```

- Schema names: `bolt.list/v1`, `bolt.info/v1`, `bolt.check/v1`, `bolt.inspect/v1`.
- `config` is `null` when no `bolt.yaml` is found. The field is present. When `bolt.yaml` exists and `bolt.local.yaml` does not, `config.local` is `null`.
- `warnings` and `errors` items are `{ "code", "message", "hint"? }`. `hint`, when present, is a copyable Fix command. A file path stays in `message`. An unknown task or flow name uses `UNKNOWN_NAME` (exit 2). An unreadable `bolt.yaml` is `CONFIG_UNREADABLE` on `check`, `list`, and `info`.
- `ok` is true exactly when the process exits 0.

`bolt version --json` is unchanged: a flat object with `version`, `plugin_api`, `manifest_format`, and `capabilities`.

Slice 1a itself does not add `bolt status` or those flags. Phase 1b (above) adds `bolt status` and inspect `plan_hash`. `--execute`, `--plan`, `--agent`, `--confirmed-by-user`, `bolt run --json`, and `bolt ai --json` are still not implemented.

### Capability selection (BOLT-EXT-2)

Singleton capability tags resolve to one handler. The map lives at the top level of `bolt.yaml` and `bolt.local.yaml`:

```yaml
capabilities:
  vcs.sync: git/pull # namespace/handler
```

`bolt.local.yaml` wins per key. `capabilities: {}` is the same as omitting the key. Fan-out tags (`doctor`, `diagnose`, `detect`, `notify`) in the map are ignored with one warning.

`bolt inspect` and `bolt run --dry-run` print the choice as `vcs.sync: git/pull (bolt.yaml)`, `(bolt.local.yaml)`, or `(auto: only match)` when exactly one built handler provides the tag. A step may name the tag: `uses: vcs.sync`.

Exit code `3` (not `2`):

- `CAPABILITY_AMBIGUOUS` — more than one built handler provides the tag and the map does not choose. The message includes a `capabilities:` snippet with one candidate.
- `CAPABILITY_MISSING` — no built handler provides the tag, and the message says how to enable a provider.
- `CAPABILITY_SELECTION_INVALID` — the chosen ref is not a handler for that tag.
- An unknown capability key, or a handler ref Bolt does not know, names the absolute config path, the key, and a "did you mean" hint.

Resolve-time (design §6 #11): a selection that names a built handler succeeds on `bolt inspect` and `bolt run --dry-run` even when another plugin that might provide the same tag is not built. A unique built match is still `(auto: only match)` when some other plugin is unbuilt. When the selection names a plugin that is not built, or no selection is set and an unbuilt plugin blocks a unique built match, the preview is incomplete: `capability unknown — plugin "<ns>" not built (Run: bolt plugin build <ns>)`. That note does not use `CAPABILITY_AMBIGUOUS`, `CAPABILITY_MISSING`, or `CAPABILITY_SELECTION_INVALID`.

Load-time: a real `bolt run` still compiles every project and user plugin in `buildRegistry`. A sibling that fails to compile can fail the whole run even when the selection already points at a built handler. "Not built" (missing or stale `bolt.plugin.json`) is not a compile failure. Skipping or soft-failing an unselected sibling is a follow-up (EXT-2.1 / BOLT-AI-2). This release does not change the loader.

`capabilitySelectionHash` is still not a field of `plan_hash`. Phase 1b hashes inspect previews; that payload does not include `capability_selection`.

**Migrate:** `uses: git/pull` and `uses: svn/update` are unchanged. Built-in `git/pull` and `svn/update` both provide `vcs.sync`; `git/info` and `svn/info` both provide `vcs.info`. A step written as `uses: vcs.sync` (or `uses: vcs.info`) must set that key, or it exits `3`. No Unreal project is required. With only one of those handlers available, Bolt selects it without a `capabilities:` key.

### Breaking: `bolt ai` reads `bolt.plugin.json` (no plugin execution) (BOLT-AI-3)

`bolt ai` and `bolt ai --stdout` no longer call `buildRegistry`, compile plugins, or `import` project/user
plugin code. They assemble the catalog from built-ins (in-process) plus each plugin's
`<plugin-root>/bolt.plugin.json`. Default mode still writes only `.bolt/ai-context.md`; `--stdout` writes
nothing under the project. Neither mode writes `.bolt/.cache`.

**Migrate:** for every project/user/path plugin, run `bolt plugin build <ns>` once (or use a newly scaffolded
plugin from `bolt plugin new`, which writes the file). Missing, invalid, or stale manifests (source
`sourcesHash` mismatch) exit `3` with the absolute path and that fix command. Step text from custom
`describe()` may be thinner; optional static `describe` strings in the JSON are supported. Builtin-only
projects keep the same context hash as before.

`bolt plugin build` executes plugin code to refresh `bolt.plugin.json` and the content-addressed cache.
A human `bolt run` and `bolt run --simulate` also refresh those files for plugins they load. Never
auto-allow `bolt plugin build` or any `bolt run` other than `--dry-run`. Do not auto-allow default
`bolt ai` (writes a file). Agents may auto-allow `bolt ai --stdout` (print-only; no project writes)
and `bolt status` (read-only).

### Breaking: all commands reject unknown and reserved flags (BOLT-CLI-1)

`bolt list`, `info`, `check`, `migrate`, `config`, `init`, `types`, `plugin new`,
`plugin list`, `self-update`, `ai`, and `version` used to ignore flags they do not
support. They now fail with exit code `2` before doing anything, using the same message
shape as `bolt run` (including `Did you mean …?` scoped to that command's flags, plus a
`Flags:` / `--help` hint). Reserved names (`json`, `agent`, `execute`, `plan`,
`confirmed-by-user`) fail with `--<name> is reserved by bolt and not supported yet`
unless the command declares them (`bolt version --json` still works; `migrate --dry-run`
still previews). **Migrate:** remove unsupported flags from scripts. Run
`bolt <command> --help` for valid flags. `bolt ai --json` no longer writes
`.bolt/ai-context.md` (it exits `2`); use `bolt ai` or `bolt ai --stdout`.

The skill (`skills/boltstack/SKILL.md`) now states this global rejection explicitly under
the run flags section; older skill text mixed run-only param rules with a broader wording.

### Breaking: strict `bolt run` / `bolt inspect` arguments

Bolt no longer silently ignores arguments it does not understand. All of the
following now fail with `[ERROR] …` and exit code `2` before anything runs:

1. **Unknown flags**, long or short: `bolt run build --dryrun` (suggests `--dry-run`), `-x`, `-xyz`.
2. **`--dry-run=<value>`**: boolean flags take no value. Before, `--dry-run=false` executed the run. Now it fails with `Flag "--dry-run" does not take a value. To run for real, just remove --dry-run.`
3. **Param values starting with `--`**: `bolt run build --extra=--verbose` used to pass `--verbose` as the value. It now fails with exit code `2`: `Param value for "--extra" may not start with "--". Pass it after a "--" separator instead: bolt run ... -- extra=--verbose`
4. **`bolt inspect --dry-run`**: `inspect` never executes, so it no longer accepts the flag. It fails with `Unknown flag "--dry-run" for "bolt inspect": bolt inspect never executes, it is already a side-effect-free preview. Remove --dry-run.`
5. **Flags before the command**: `bolt --dry-run run deploy` used to drop the flag and **execute**. Only `-h`, `--help`, and `--version` are allowed before the command. A near miss such as `bolt --verison` suggests the match: `Unknown global flag "--verison". Did you mean "--version"?`. Help wins (`bolt --help --version` shows help, exit 0); `--version` otherwise must be alone and takes no value.
6. **Reserved names** `dry-run`, `simulate`, `json`, `agent`, `execute`, `plan`, `confirmed-by-user` cannot be params, neither as `--name=value` nor as `name=value` after `--`. Only `--dry-run` and `--simulate` (added by BOLT-P0-1, see below) are implemented; the others fail with `--<name> is reserved by bolt and not supported yet`. Using one as a param name fails with a rename hint: `--plan=x` prints `--plan is reserved by bolt and not supported yet. If this is a task param, rename it, e.g. in bolt.yaml use my_plan and pass -- my_plan=x.`, and `-- plan=x` prints `"plan" cannot be used as a param name (--plan is reserved by bolt and not supported yet). Rename the param, e.g. in bolt.yaml use my_plan and pass -- my_plan=x.`
7. **`help` is also reserved after the command**, in addition to the 7 reserved names above (it is handled separately): `--help=<value>` and `help=<value>` after `--` used to be passed as a task param (so `bolt run mark --help=1` **ran the task**). Now `--help=1` fails with `--help takes no value. Use: bolt run --help. …`, and `-- help=1` fails with `"help" cannot be used as a param name (it is a bolt flag). Rename the param, e.g. in bolt.yaml use my_help and pass -- my_help=1.` Bare `--help` / `-h` still show help.

Reserved names are case-sensitive: `--PLAN=x` and `-- Plan=x` are ordinary params.

### Breaking: exit code `2` for unknown commands, unknown tasks, and a missing task

8. **Mistyped command**: `bolt rn mark` used to print the full usage and exit `1`. It now prints a short suggestion and the list of commands, and exits `2`: `Unknown command "rn". Did you mean "run"?` (also for nested commands, e.g. `bolt plugin nw`).
9. **Unknown task or flow**: `bolt run mrk` / `bolt inspect mrk` exited `1` with `Unknown task or flow: "mrk"`. They now exit `2` with `Unknown task "mrk". Did you mean "mark"?` followed by the project's tasks and flows, before any log file is created. When the only match differs by case (`bolt run Mark` → `mark`), the message adds `Task names are case-sensitive.`
10. **No task given**: `bolt run` / `bolt inspect` without a name exited `1` with a fixed `bolt run build start` example. They now exit `2` and list the project's actual tasks and flows (`Example: bolt run <first task>`); outside a project they point to `bolt list` / `bolt init`.

### Breaking: `--dry-run` runs nothing and writes nothing (BOLT-P0-1)

This supersedes the #27 change below. `bolt run … --dry-run` is now a
pure static preview: it reads `bolt.yaml`, resolves the plan like `bolt inspect`, and
prints every step as `would run …`. It no longer:

- imports, compiles, or installs plugins (no `.bolt/.cache`, no `bun install`);
- calls plugin `onInit`, `onBeforeStep`, `onAfterStep`, or handlers;
- reaches local actions at all (`uses: ./…`); #27 already stopped running them, and a dry run now only checks that `action.yaml` and a run script exist;
- spawns any process, including `git` for notifications;
- creates `.bolt/` or writes a log file under `.bolt/logs/`.

The output ends with `Nothing was executed …` and points to `--simulate`. Built-in
handler params are validated against their schema (a misspelled key such as `dest`
for `fs/copy` is reported as `missing param "dst" (you passed "dest"; did you mean "dst"?)`),
and `call:` targets and local action scripts are checked. Config problems a real run would
hit (unknown plugin namespace or op, bad built-in params, missing action script) are marked
with `!` and exit `3`. Third-party plugin params are not validated and are not an error.
A `plugins:` entry whose `path` does not exist is also reported. Param values with spaces
are quoted in the output (`dest="b c"`). A dry run cannot show
the exact command a plugin handler builds (for example the `Build.bat` line from
`ue/build`), because the handler is not called.

New flag `--simulate`: the previous plugin-level preview. Plugins load and their hooks
and handlers run with `ctx.dryRun = true`; `run:` steps and local actions are skipped;
a missing `action.yaml` or run script still fails the step; a log file is written;
notifications are not sent. Plugins may still have side effects.
`--dry-run` and `--simulate` cannot be combined. With the library API, `dryRun: true`
still behaves like `--simulate` (plugins load and hooks run), and now also skips local
actions; a pure library dry run is tracked as BOLT-DX-3.

### Breaking: exit code `3` for config errors (BOLT-P0-1)

`bolt.yaml` missing, unparseable, failing the schema, or describing an invalid task
graph (unknown `call:` target, call cycle, malformed `uses:` ref, legacy `task/<name>`)
now exits `3` instead of `1`, before anything runs and before a log file is created.
This applies to `bolt run` (with or without `--dry-run`), `inspect`, `list`, `info`,
`check`, `ai`, `plugin list`, `migrate`, and `config` (when `bolt.yaml` is missing;
`bolt config` still creates it from `bolt.template.yaml` when that exists). Both now print
the same `[ERROR] bolt.yaml not found in …` message as the other commands. `bolt plugin new`
is unchanged. A `bolt.yaml` that exists but cannot be read also exits `3`, with
`Permission denied reading <path>. Check the file permissions …` (the error's `code` is
`CONFIG_UNREADABLE`; missing and invalid files are `CONFIG_NOT_FOUND` and `CONFIG_INVALID`).
Errors say how to fix them, for example
`bolt.yaml not found in <dir> or any parent directory.` followed by
`Run bolt from your project directory, or create one with bolt init.`

Exit codes: `0` success, `1` task failure, `2` usage error, `3` config error,
`4` denied (reserved for `AI_FORBIDDEN`, used once AI invocation is enabled).

### Improved error hints

- Rename hints for a reserved param name now use one neutral form for every name: `my_<name>` with `-` turned into `_` (`plan` → `my_plan`, `dry-run` → `my_dry_run`, `help` → `my_help`).
- Values in suggested commands are quoted when needed, so they copy-paste correctly: `-- plan="yes please"` suggests `-- my_plan="yes please"`.
- `-- dry-run=false` (or `0`, `no`, `off`) says to just remove `--dry-run` to run for real.
- `bolt run --help`, `bolt plugin new --help` and other command help now show `USAGE bolt run …` instead of the script path (for example `/$bunfs/root/bolt`).
- Short mistypes no longer guess wildly (`bolt x` / `bolt run d` give no suggestion). Adjacent letter swaps still suggest (`mrak` → `mark`, `buidl` → `build`). Ambiguous prefixes list matches (`Did you mean "build" or "build-editor"?`). Long task lists truncate after 10 names in declaration order (`and N more (see bolt list)`).
- Common mix-ups: `bolt help` → `bolt --help`; `bolt update` / `upgrade` → `bolt self-update`; `bolt build` (when `build` is a task) → `bolt run build`. `bolt plugin` with no subcommand exits `2` with the subcommand list. A flow typo says `Unknown flow "…"`.

### Fixed

- `--simulate` and real runs (this also affects `main` and earlier releases) with a misspelled built-in param, for example
  `uses: fs/copy` with `dest:` instead of `dst:`, printed the native error
  `The "paths[1]" property must be of type string` twice. It now prints once:
  `Invalid params for "fs/copy": missing param "dst" (you passed "dest"; did you mean "dst"?)`,
  lists the handler's params, and says to fix the step's `with:` in `bolt.yaml`.
  Built-in `fs`, `json`, `git`, and `svn` handlers now validate their params before
  running. Keys a handler does not use (for example run-wide `--key=value` params) are
  still allowed.

### Migration: exit codes (#30 and BOLT-P0-1)

| Code | Meaning                                                                                                                                      | Before                              |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| `0`  | Success                                                                                                                                      | `0`                                 |
| `1`  | Task failure (a step failed while running)                                                                                                   | `1`                                 |
| `2`  | Usage error: unknown command, flag, task, or flow; malformed param; no task given; `bolt plugin` with no subcommand                          | `1`                                 |
| `3`  | Config error: `bolt.yaml` missing, unreadable, unparseable, failing the schema, invalid task graph, or a config problem found by `--dry-run` | `1` (`0` for some dry-run problems) |
| `4`  | Denied: reserved for `AI_FORBIDDEN` (AI permission / confirmation, with the AI features); not used for config files                          | -                                   |

- `bolt run x || exit`, `bolt run x || …`, and `if ! bolt run x` are **unchanged**:
  any non-zero still fails.
- Scripts that used `if [ $? -eq 1 ]` or PowerShell `if ($LASTEXITCODE -eq 1)` to
  mean "any failure" should use `-ne 0` instead (same operator in bash and PowerShell).
- Scripts that used `-eq 1` to detect a broken or missing `bolt.yaml` must check
  `-eq 3` instead. `bolt check` exits `3` when `bolt.yaml` is invalid or missing.
- To tell failures apart: `1` = a task failed, `2` = fix the command line,
  `3` = fix `bolt.yaml` (including its file permissions), `4` = denied (AI permission or
  confirmation).

### Migration

- Values that start with `--`: pass them after a bare `--` separator, which
  accepts only `key=value` params:

  ```bash
  # before
  bolt run build --extra=--verbose
  # after
  bolt run build -- extra=--verbose
  ```

- Tool flags that never change: put them in `bolt.yaml` (`with:` or `vars`)
  instead of on the command line.
- A step param named like a reserved flag (for example `plan`): rename it
  (for example `my_plan`) in `bolt.yaml` and on the command line.
- A step param named `help`: before, `bolt run x --help=foo` passed `help=foo`
  to steps; now it exits with code `2`. Rename the param (for example `my_help`)
  everywhere at once: the step `with:` keys and every `${{ params.help }}`
  reference in `bolt.yaml`, and on the command line (`-- my_help=foo`).
- Move flags placed before the command to after it: `bolt run deploy --dry-run`.
- **Relying on `--dry-run` to run plugin code** (hooks, handler dry-run logging,
  compiling a project plugin, `bun install`, or a log file): use `--simulate`
  instead. To build a project plugin or install its dependencies, run a real task once.

### Changed

- (#27, superseded by BOLT-P0-1 above) `--dry-run` skipped `run:` steps and local actions but still loaded plugins and called plugin hooks and handlers (with `ctx.dryRun=true`); previously it could also run local actions. That plugin-level preview is now `--simulate`; `--dry-run` runs no plugin code at all.

### Plugin API v2: Added

- Plugin API v2 (BOLT-EXT-1). Plugins opt in with `definePlugin({ apiVersion: 2 })` or the class instance field `apiVersion = 2;`. A plugin without `apiVersion` is still v1 and behaves exactly as before. See the [migration guide](/guides/migrating-to-plugin-api-2).
- Handler results: v2 handlers may return `ok()` / `warn()` / `fail()` / `skipped()` (or a `HandlerResult` literal). A returned `fail` fails the step like a throw (`HANDLER_FAILED`, after `onAfterStep`). An invalid result fails with `RESULT_INVALID`. Unknown result fields only warn (`RESULT_UNKNOWN_KEY`) and are dropped. Oversize values are truncated with `RESULT_TRUNCATED`. Return values of v1 plugins are still ignored.
- `ctx.emit(event)` for v1 and v2 plugins and lifecycle hooks. Events are printed on the run output and written to `.bolt/logs/bolt_<timestamp>.log`. `ctx.emit` is optional in `BoltPluginContext` until the next plugin API major; `BoltPluginContextV2` has it required. `createTestContext()` records events for unit tests.
- Capability tags: `defineHandler({ capability })` and `@handler({ capability })` (v2 only), with a core-owned vocabulary, `x-<vendor>.` and `<namespace>.` forms, and reserved core areas. Tags appear in the plugin manifest, the AI context, and the generated plugin reference. `PluginRegistry.findByCapability()` looks handlers up by tag.
- `bolt version --json` prints `version`, `plugin_api` (`[1, 2]`), `manifest_format`, and `capabilities` (`handler-results`, `capability-tags`, `plugin-api-2`).
- Release workflow check that fails while an unreleased version placeholder remains.

### Plugin API v2: Changed

- **Built-in git/svn AI permissions changed.** These handlers used to be `ai: false` for everything. Now: `git/info` and `svn/info` are `ai: true` (read-only; for AI invocations `path` must be inside the project directory); `git/status` and `svn/status` are `ai: "confirm"` (`git status` runs the repository's `core.fsmonitor` command); `git/pull`, `git/checkout`, `git/clone`, `svn/update`, `svn/cleanup`, `svn/revert`, `svn/commit`, and `svn/add` stay `ai: false`. This changes `.bolt/ai-context.md` and its context hash.
- Built-in git and svn are now plugin API v2 plugins tagged `vcs.sync` (`git/pull`, `svn/update`) and `vcs.info` (`git/info`, `svn/info`). `git/info`, `git/status`, `svn/info`, and `svn/status` declare a `path` param schema, so a missing `path` is reported as a param error.
- `git/info` and `svn/info` with a `path` outside the project directory: human runs behave as before and succeed, but now print a warning that AI invocations will reject the path, with the fix. `ue/info` is unchanged and still reads engine and project paths anywhere.
- **AI invocations of `git/info` and `svn/info` reject a `path` outside the project directory** with `AI_FORBIDDEN` (exit code `4`, denied) and a fix (use a path under the project, or a `run:` step for other repositories).
- **Migration: `git/info` and `svn/info` resolve a relative `path` against the `bolt.yaml` directory**, not the current working directory. Example: with `bolt.yaml` in `/proj` and running from `/proj/tools`, `path: ../Engine` used to resolve to `<cwd>/../Engine` (`/proj/Engine`); it now resolves to `<bolt.yaml dir>/../Engine` (`/Engine`). To keep the old target, use an absolute path or adjust the relative path so it is relative to the `bolt.yaml` directory (here `path: Engine`).
- Plugin API version errors now list the supported versions and, for a newer plugin, tell you to run `bolt self-update`. A class plugin with a `static apiVersion` that differs from its instance field is rejected; a matching one warns.
- Manifest format is now 2. After upgrading, run `bolt ai` to regenerate `.bolt/ai-context.md`; `bolt run` warns (`AI_CONTEXT_STALE`) until you do.
- **AI invocations: project paths are checked after resolving symlinks.** For `git/info`, `svn/info`, `fs/*`, and `json/*`, an AI invocation is rejected with `AI_FORBIDDEN` (exit code `4`) when a path, read or write, resolves outside the project directory. This includes an in-project symlink to an outside directory, or a path that cannot be resolved (symlink loop, dangling symlink, permission error). Human runs are unaffected: `fs/*` and `json/*` behave exactly as before (literal `../x` is still rejected, symlinks are followed silently), and `git/info` / `svn/info` warn only for a literal out-of-project path such as `../Engine` (a symlink escape is silent, as before).

### Plugin API v2: Fixed

- The run log (`.bolt/logs/bolt_<timestamp>.log`) could lose its final lines because `bolt run` exited before `Logger.close()` finished flushing the file. `bolt run` now waits for the flush.

### Plugin API v2: types

- `BoltPluginHandler`, `HandlerDef.fn`, and `defineHandler` now return `Promise<void | HandlerResult>`. `PLUGIN_API_VERSION` is `2`; use `SUPPORTED_PLUGIN_API_VERSIONS` for the accepted set.

### Plugin API v2: Deferred (not in BOLT-EXT-1)
