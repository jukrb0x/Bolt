## Unreleased

### Breaking: strict `bolt run` / `bolt inspect` arguments

Bolt no longer silently ignores arguments it does not understand. All of the
following now fail with `[ERROR] …` and exit code `2` before anything runs:

1. **Unknown flags**, long or short: `bolt run build --dryrun` (suggests `--dry-run`), `-x`, `-xyz`.
2. **`--dry-run=<value>`**: boolean flags take no value. Before, `--dry-run=false` executed the run. Now it fails with `Flag "--dry-run" does not take a value. To run for real, just remove --dry-run.`
3. **Param values starting with `--`**: `bolt run build --extra=--verbose` used to pass `--verbose` as the value. It now fails with exit code `2`: `Param value for "--extra" may not start with "--". Pass it after a "--" separator instead: bolt run ... -- extra=--verbose`
4. **`bolt inspect --dry-run`**: `inspect` never executes, so it no longer accepts the flag. It fails with `Unknown flag "--dry-run" for "bolt inspect": bolt inspect never executes, it is already a side-effect-free preview. Remove --dry-run.`
5. **Flags before the command**: `bolt --dry-run run deploy` used to drop the flag and **execute**. Only `-h`, `--help`, and `--version` are allowed before the command. A near miss such as `bolt --verison` suggests the match: `Unknown global flag "--verison". Did you mean "--version"?`. Help wins (`bolt --help --version` shows help, exit 0); `--version` otherwise must be alone and takes no value.
6. **Reserved names** `dry-run`, `simulate`, `json`, `agent`, `execute`, `plan`, `confirmed-by-user` cannot be params, neither as `--name=value` nor as `name=value` after `--`. Only `--dry-run` is implemented; the others fail with `--<name> is reserved by bolt and not supported yet`. Using one as a param name fails with a rename hint: `--plan=x` prints `--plan is reserved by bolt and not supported yet. If this is a task param, rename it, e.g. in bolt.yaml use my_plan and pass -- my_plan=x.`, and `-- plan=x` prints `"plan" cannot be used as a param name (--plan is reserved by bolt and not supported yet). Rename the param, e.g. in bolt.yaml use my_plan and pass -- my_plan=x.`
7. **`help` is also reserved after the command**, in addition to the 7 reserved names above (it is handled separately): `--help=<value>` and `help=<value>` after `--` used to be passed as a task param (so `bolt run mark --help=1` **ran the task**). Now `--help=1` fails with `--help takes no value. Use: bolt run --help. …`, and `-- help=1` fails with `"help" cannot be used as a param name (it is a bolt flag). Rename the param, e.g. in bolt.yaml use my_help and pass -- my_help=1.` Bare `--help` / `-h` still show help.

Reserved names are case-sensitive: `--PLAN=x` and `-- Plan=x` are ordinary params.

### Breaking: exit code `2` for unknown commands, unknown tasks, and a missing task

8. **Mistyped command**: `bolt rn mark` used to print the full usage and exit `1`. It now prints a short suggestion and the list of commands, and exits `2`: `Unknown command "rn". Did you mean "run"?` (also for nested commands, e.g. `bolt plugin nw`).
9. **Unknown task or flow**: `bolt run mrk` / `bolt inspect mrk` exited `1` with `Unknown task or flow: "mrk"`. They now exit `2` with `Unknown task "mrk". Did you mean "mark"?` followed by the project's tasks and flows, before any log file is created. When the only match differs by case (`bolt run Mark` → `mark`), the message adds `Task names are case-sensitive.`
10. **No task given**: `bolt run` / `bolt inspect` without a name exited `1` with a fixed `bolt run build start` example. They now exit `2` and list the project's actual tasks and flows (`Example: bolt run <first task>`); outside a project they point to `bolt list` / `bolt init`.

### Improved error hints

- Rename hints for a reserved param name now use one neutral form for every name: `my_<name>` with `-` turned into `_` (`plan` → `my_plan`, `dry-run` → `my_dry_run`, `help` → `my_help`).
- Values in suggested commands are quoted when needed, so they copy-paste correctly: `-- plan="yes please"` suggests `-- my_plan="yes please"`.
- `-- dry-run=false` (or `0`, `no`, `off`) says to just remove `--dry-run` to run for real.
- `bolt run --help`, `bolt plugin new --help` and other command help now show `USAGE bolt run …` instead of the script path (for example `/$bunfs/root/bolt`).
- Short mistypes no longer guess wildly (`bolt x` / `bolt run d` give no suggestion). Adjacent letter swaps still suggest (`mrak` → `mark`, `buidl` → `build`). Ambiguous prefixes list matches (`Did you mean "build" or "build-editor"?`). Long task lists truncate after 10 names in declaration order (`and N more (see bolt list)`).
- Common mix-ups: `bolt help` → `bolt --help`; `bolt update` / `upgrade` → `bolt self-update`; `bolt build` (when `build` is a task) → `bolt run build`. `bolt plugin` with no subcommand exits `2` with the subcommand list. A flow typo says `Unknown flow "…"`.

### Migration

- Values that start with `--`: pass them after a bare `--` separator, which
  accepts only `key=value` params:

  ```bash
  # before
  bolt run build --extra=--verbose
  # after
  bolt run build -- extra=--verbose
  ```

- Tool flags that never change: put them in `bolt.yaml` (`with:` or `vars`)
  instead of on the command line.
- A step param named like a reserved flag (for example `plan`): rename it
  (for example `my_plan`) in `bolt.yaml` and on the command line.
- A step param named `help`: before, `bolt run x --help=foo` passed `help=foo`
  to steps; now it exits with code `2`. Rename the param (for example `my_help`)
  everywhere at once: the step `with:` keys and every `${{ params.help }}`
  reference in `bolt.yaml`, and on the command line (`-- my_help=foo`).
- Move flags placed before the command to after it: `bolt run deploy --dry-run`.
- **Exit codes for usage mistakes are now `2`** (unknown command, unknown task/flow,
  missing task, `bolt plugin` with no subcommand, strict flag errors). Task failures
  still exit `1`.

  - `bolt run x || exit`, `bolt run x || …`, and `if ! bolt run x` are **unchanged** (any non-zero still fails).
  - Scripts that used `if [ $? -eq 1 ]` or PowerShell `if ($LASTEXITCODE -eq 1)` to
    mean "any failure" should use `-ne 0` instead (same operator in bash and PowerShell).
  - To distinguish usage errors from task failures: `2` = usage, `1` = task failure.
  - Config errors (`bolt.yaml` missing/invalid) will exit `3` in this same release,
    shipping together with **BOLT-P0-1**. Until BOLT-P0-1 lands on main they still
    exit `1`; do not treat exit `1` as "config error".

### Plugin API v2: Added

- Plugin API v2 (BOLT-EXT-1). Plugins opt in with `definePlugin({ apiVersion: 2 })` or the class instance field `apiVersion = 2;`. A plugin without `apiVersion` is still v1 and behaves exactly as before. See the [migration guide](/guides/migrating-to-plugin-api-2).
- Handler results: v2 handlers may return `ok()` / `warn()` / `fail()` / `skipped()` (or a `HandlerResult` literal). A returned `fail` fails the step like a throw (`HANDLER_FAILED`, after `onAfterStep`). An invalid result fails with `RESULT_INVALID`. Unknown result fields only warn (`RESULT_UNKNOWN_KEY`) and are dropped. Oversize values are truncated with `RESULT_TRUNCATED`. Return values of v1 plugins are still ignored.
- `ctx.emit(event)` for v1 and v2 plugins and lifecycle hooks. Events are printed on the run output and written to `.bolt/logs/bolt_<timestamp>.log`. `ctx.emit` is optional in `BoltPluginContext` until the next plugin API major; `BoltPluginContextV2` has it required. `createTestContext()` records events for unit tests.
- Capability tags: `defineHandler({ capability })` and `@handler({ capability })` (v2 only), with a core-owned vocabulary, `x-<vendor>.` and `<namespace>.` forms, and reserved core areas. Tags appear in the plugin manifest, the AI context, and the generated plugin reference. `PluginRegistry.findByCapability()` looks handlers up by tag.
- `bolt version --json` prints `version`, `plugin_api` (`[1, 2]`), `manifest_format`, and `capabilities` (`handler-results`, `capability-tags`, `plugin-api-2`).
- Release workflow check that fails while an unreleased version placeholder remains.

### Plugin API v2: Changed

- **Built-in git/svn AI permissions changed.** These handlers used to be `ai: false` for everything. Now: `git/info` and `svn/info` are `ai: true` (read-only; for AI invocations `path` must be inside the project directory); `git/status` and `svn/status` are `ai: "confirm"` (`git status` runs the repository's `core.fsmonitor` command); `git/pull`, `git/checkout`, `git/clone`, `svn/update`, `svn/cleanup`, `svn/revert`, `svn/commit`, and `svn/add` stay `ai: false`. This changes `.bolt/ai-context.md` and its context hash.
- Built-in git and svn are now plugin API v2 plugins tagged `vcs.sync` (`git/pull`, `svn/update`) and `vcs.info` (`git/info`, `svn/info`). `git/info`, `git/status`, `svn/info`, and `svn/status` declare a `path` param schema, so a missing `path` is reported as a param error.
- `git/info` and `svn/info` with a `path` outside the project directory: human runs behave as before and succeed, but now print a warning that AI invocations will reject the path, with the fix. `ue/info` is unchanged and still reads engine and project paths anywhere.
- **AI invocations of `git/info` and `svn/info` reject a `path` outside the project directory** with `AI_FORBIDDEN` (exit code `4`, permission denied) and a fix (use a path under the project, or a `run:` step for other repositories).
- **Migration: `git/info` and `svn/info` resolve a relative `path` against the `bolt.yaml` directory**, not the current working directory. Example: with `bolt.yaml` in `/proj` and running from `/proj/tools`, `path: ../Engine` used to resolve to `<cwd>/../Engine` (`/proj/Engine`); it now resolves to `<bolt.yaml dir>/../Engine` (`/Engine`). To keep the old target, use an absolute path or adjust the relative path so it is relative to the `bolt.yaml` directory (here `path: Engine`).
- Plugin API version errors now list the supported versions and, for a newer plugin, tell you to run `bolt self-update`. A class plugin with a `static apiVersion` that differs from its instance field is rejected; a matching one warns.
- Manifest format is now 2. After upgrading, run `bolt ai` to regenerate `.bolt/ai-context.md`; `bolt run` warns (`AI_CONTEXT_STALE`) until you do.
- **AI invocations: project paths are checked after resolving symlinks.** For `git/info`, `svn/info`, `fs/*`, and `json/*`, an AI invocation is rejected with `AI_FORBIDDEN` (exit code `4`) when a path, read or write, resolves outside the project directory. This includes an in-project symlink to an outside directory, or a path that cannot be resolved (symlink loop, dangling symlink, permission error). Human runs are unaffected: `fs/*` and `json/*` behave exactly as before (literal `../x` is still rejected, symlinks are followed silently), and `git/info` / `svn/info` warn only for a literal out-of-project path such as `../Engine` (a symlink escape is silent, as before).

### Plugin API v2: Fixed

- The run log (`.bolt/logs/bolt_<timestamp>.log`) could lose its final lines because `bolt run` exited before `Logger.close()` finished flushing the file. `bolt run` now waits for the flush.

### Plugin API v2: types

- `BoltPluginHandler`, `HandlerDef.fn`, and `defineHandler` now return `Promise<void | HandlerResult>`. `PLUGIN_API_VERSION` is `2`; use `SUPPORTED_PLUGIN_API_VERSIONS` for the accepted set.
