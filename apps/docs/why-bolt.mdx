## The problem

A game project's daily routine is a chain of small, manual steps. On an Unreal Engine team it often
looks like this: update the engine from git, update the project from SVN in TortoiseSVN, run
`Build.bat` with the right target and configuration, regenerate project files when something changed,
then launch the editor. Each step is easy. Doing them in the right order, every day, on every machine,
is where time goes.

Teams usually solve this with a folder of batch or shell scripts. Those scripts tend to hard-code one
person's paths, drift between machines, fail in ways that are hard to read, and stay with whoever wrote
them.

## What Bolt is

Bolt is a general-purpose CLI that turns that routine into named commands your team shares:

- **A committed workflow contract.** `bolt.yaml` lists the project's tasks and flows. It lives in the
  repository, so new teammates get the same commands as everyone else.
- **Machine settings kept separate.** Engine and project paths that differ per machine go in an
  optional, gitignored `bolt.local.yaml`, which deep-merges over the plugin config in `bolt.yaml`.
- **Engine knowledge in plugins, not in the core.** The core resolves and runs tasks. What "build the
  editor" means for Unreal Engine lives in the built-in `ue` plugin. Version control steps come from
  the `git` and `svn` plugins.
- **A single binary.** `bolt` is one executable installed under `~/.bolt/bin`, updated with
  `bolt self-update`. Plugins are TypeScript modules that Bolt compiles itself.

## Design choices

**Two building blocks, one verb.** A task is a named list of steps. A flow is an ordered set of tasks.
`bolt run` runs either. Tasks run in the order you type them (`bolt run update build start`), and a
single flow name runs that flow. Bolt never reorders steps.

**Fail-fast by default.** In a flow, the first failing task stops the run unless that task is listed in
`continue_on_fail`. A single step can opt out with `continue-on-error: true`.

**Three kinds of step.** `uses` calls a plugin handler (`ue/build`) or a project-local action, `call`
reuses another task, and `run` executes a shell command. Each step uses exactly one of these keys.

**Params instead of variants.** `--key=value` on the command line applies to the whole run and
overrides each step's `with:` values, so `bolt run build --target=client --config=shipping` reuses the
same `build` task.

**One plan for preview and execution.** `bolt inspect <names>` and `bolt run <names> --dry-run` show
the resolved steps that `bolt run` would execute. In the current release, `--dry-run` still calls plugin
handlers (with `ctx.dryRun=true`) and runs local actions; only `run:` shell steps are skipped.

**Layered plugins.** Bolt looks for plugins in four places: built-in, user (`~/.bolt/plugins`), project
(`.bolt/plugins`), and explicit `path` entries in `bolt.yaml`. A later layer replaces a plugin with the
same namespace, so you can override a built-in handler without forking Bolt.

**Usable as a library.** The `boltstack` npm package exposes `run`, `loadConfig`, the built-in plugins,
and the runner to Node.js and Bun scripts. See [Library usage](/api/library-usage).

## How Bolt fits with other tools

Bolt sits above the engine's own tools and below (or beside) your CI system. It does not replace
either.

| Tool | What it does | How Bolt relates |
| --- | --- | --- |
| Engine build tools (UnrealBuildTool, `Build.bat`, RunUAT) | Compile and package the engine and game | Bolt calls them. `ue/build` runs `Build.bat` with the target and configuration from `bolt.yaml`. |
| Batch and shell scripts | Ad-hoc automation | `run:` steps can still call them, but tasks, flows, and params replace most of the glue. |
| CI servers (Jenkins, TeamCity, GitHub Actions) | Schedule and distribute builds across agents | Bolt runs on a developer machine or inside a CI job. It has no scheduler, agents, or build farm. |
| Source control clients (git, SVN, TortoiseSVN) | Version control | The `git` and `svn` plugins and `ue/update_engine` / `ue/update_project` wrap the daily update. |

## When not to use Bolt

Bolt is a young tool. Today it is a poor fit if you need:

- **Distributed or scheduled builds.** Use a CI system or build farm. You can call `bolt run` from it.
- **Unreal Engine builds on macOS or Linux.** The `ue` plugin's build, launch, and kill handlers target
  Windows (`Build.bat`, `Win64`, `taskkill`).
- **Perforce.** Version control support is git and SVN.
- **Cooking and packaging.** There is no built-in BuildCookRun handler. A `run:` step can call RunUAT
  directly.
- **Parallel steps.** Steps and tasks run one after another.
- **Machine-readable output.** Commands print human-readable text. Structured `--json` output is
  designed but not shipped (see [AI overview](/ai/overview)).
- **Other notification channels.** Built-in providers are WeCom and Telegram.
